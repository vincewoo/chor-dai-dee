# Review: PR #155 — feat(feed): badge games played against max-difficulty bots

**PR**: https://github.com/vincewoo/chor-dai-dee/pull/155
**Author**: @julo15 (Julian Lo)
**Branch**: `julo/feed-max-bots-badge` → `main`
**Review round**: 1
**Date reviewed**: 2026-08-05

## Summary

Records the frozen bot-difficulty tier on `game_history`, and renders a gold **⚔️ MAX BOTS** chip
on finished games that were pinned to the ceiling tier *and* actually seated a bot. One shared
`MaxBotsChip` serves the activity feed, the home screen's Recent list, and the score dialog.

## How It Works

**Write path.** `Room` snapshots exactly one `botPolicy` per game
(`RoomManager.refreshBotPolicy`, driven by `configureBotPolicyForRoster()`, which resolves to
`MAX_BOT_DIFFICULTY` when the host's `forceMaxBots` toggle is on and `adaptive` otherwise). The PR
threads `room.botPolicy.difficulty` — deliberately the policy that plays, not the `forceMaxBots`
toggle that requested it — into all five `saveGameHistory` call sites in `server/index.js`:
`start_game` (1777), `host_rematch` (2183), game-over (1208), dragon-win (851), and
`recordAbandonedGame` (273). The opening `in_progress` write and the terminal write both carry it;
`ON CONFLICT` re-applies it through `COALESCE(?, bot_difficulty)`, so a terminal write can heal a
row opened by a build that predates the column, while a NULL can never clobber a good value.
(Placeholder/binding counts verified: 13 INSERT + 8 UPDATE = 21, matching the bound array.)

**Schema.** `bot_difficulty TEXT` is added both to the `CREATE TABLE` (fresh databases) and via a
`PRAGMA table_info` + guarded `ALTER TABLE ADD COLUMN` block at `server/db.js:623-638`, following
the same idiom already used for `round_stats` and `user_preferences`. NULL means *unknown* and is
never backfilled, on the grounds that every pre-tier row ran full-strength argmax and reconstructing
them would badge the whole archive.

**Read path.** `getActivityFeed` derives one boolean per row —
`row.bot_difficulty === MAX_BOT_DIFFICULTY_ID && participants.some(p => p.isBot)` — where
`MAX_BOT_DIFFICULTY_ID` is db.js's local copy of `BotPolicy.MAX_BOT_DIFFICULTY`, pinned by a new
test. The two-clause AND answers both halves in one place: max difficulty is a *room* setting, so a
table that filled with four humans carries it with nothing to apply it to.

**Render path.** `GET /api/activity` feeds two consumers. `ActivityFeed.jsx` → `ActivityFeedV2`
renders the chip in the card's meta row (now `flex-wrap`, so QUIT + PRIVATE + MAX BOTS can coexist
at 320px). `Lobby.jsx` fetches the same endpoint for `recentGames` → `HomeScreenV2`'s Recent list,
and its `handleGameClick` maps `maxBots` into the `ScoreDialog` payload.

## Complexity & Risk

**Low-to-medium.** 12 files, +333/−13, one commit, and the change is almost entirely additive: a
nullable column, one derived boolean, one presentational component, three call sites. It is easy to
revert (the column can simply be left in place and ignored).

The risk is concentrated in three places, none of which is the badge logic itself:

1. **The migration**, because `saveGameHistory`'s INSERT now *unconditionally* names the new column.
   That turns a schema-drift bug from "a badge is missing" into "the game-start write throws," and
   that write is inside a `withTransaction` that also carries the opening participant rows.
2. **The `'competitive'` collision.** `DEFAULT_BOT_DIFFICULTY` and `MAX_BOT_DIFFICULTY` are the same
   string, so a `Room` reports the max tier from its constructor onward. The badge is correct today
   only because every production game-start path happens to reconfigure the policy first — an
   implicit, untested cross-file ordering invariant.
3. **The payload**, where the PR's central privacy claim is not actually enforced (see Critical).

The three UI surfaces themselves are cosmetic and low-risk; `MaxBotsChip` has no branching.

## Findings

### Critical

**C1. The raw `bot_difficulty` tier string is shipped to every client, contradicting three claims
this PR ships alongside it.** `server/db.js:2535-2548`

`getActivityFeed`'s CTE does `SELECT * FROM game_history` and the row mapper returns
`{ ...row, participants, maxBots, participants_json: undefined }`. It strips `participants_json`
but not `bot_difficulty`, so the raw tier is serialized into every game object on the public,
unauthenticated `GET /api/activity`. Two reviewers verified this live against a scratch database:
`{"bot_difficulty":"adaptive", ..., "maxBots":false}` is present for *every* game, not only
max-difficulty ones.

This is not a hypothetical style point — it falsifies three statements added by this same PR:

- `docs/BOT-DIFFICULTY.md`: "The client never compares tier ids."
- `CLAUDE.md`: "every column added to this table ships to every client; that is why the derived
  `maxBots` boolean lives server-side."
- `server/db.js:619-622`: "Nothing continuous belongs in this table."

All three are true of the *client code* and false of the *wire payload*. The whole architectural
argument of the PR is that the tier must not cross the boundary; the code lets it cross.

Today's concrete exposure is small — only `'adaptive'` and `'competitive'` are reachable through
the live toggle, and the continuous temperature is not on this table — but there is one real leak:
a room with `forceMaxBots` on and four humans stores `'competitive'` and is deliberately *not*
badged, yet the raw field still discloses that the host toggled Max Bots for that game.

The bigger cost is the precedent. The column is `TEXT` with no `CHECK` constraint (unlike `status`
in the same `CREATE TABLE`), and `page.*` means any future column is public by default. The PR
documents that trap at length and then does not close it.

**Fix:** add `bot_difficulty: undefined` beside `participants_json: undefined` (or select columns
explicitly), plus a regression test asserting
`JSON.parse(JSON.stringify(game)).bot_difficulty === undefined`. The current tests only assert
`maxBots`'s value and never that the raw column is absent — which is exactly why this shipped with a
green suite.

### Suggestions

**S1. Boot-time `ALTER TABLE` race can lose an entire game's opening rows.** `server/db.js:623-638`,
`server/index.js:3435`

The ALTER is scheduled from *inside* the async `PRAGMA table_info` callback, so it lands at the back
of sqlite3's queue rather than in `db.serialize()`'s synchronous body — and `server.listen()` never
waits for `initDb()` to drain. Reproduced empirically: requiring `db.js` against a database missing
the column and calling `saveGameHistory()` on the next tick throws
`SQLITE_ERROR: table game_history has no column named bot_difficulty`; a short wait makes the same
call succeed.

Because `saveGameHistory`'s INSERT unconditionally lists `bot_difficulty`, it errors outright rather
than degrading, and the surrounding `withTransaction` (`server/index.js:1757-1797`) rolls back the
opening `game_participants` rows too — caught by a bare `console.error` with no retry. If that game
is then abandoned or the process dies, `sweepAbandonedGames()` can't help: it only updates rows
already `in_progress`, and no row was ever written. The game is permanently invisible.

Honest scoping: the window is one-time per environment and requires a `start_game` within roughly a
second of process boot, which is implausible in practice (a game start needs a socket, a room and a
roster). The pattern is also identical to five existing migration blocks in the same file, so this
is systemic debt rather than a novel defect. But this PR is the first to put a migrated column on
the game-start critical path inside a rolled-back transaction, which is what raises the stakes.

Cheapest durable fix: gate `server.listen()` on an `initDb()` completion promise. Cheapest local
fix: issue the `ALTER` unconditionally in the serialize body and swallow the `duplicate column`
error, skipping the async PRAGMA hop entirely.

**S2. `DEFAULT_BOT_DIFFICULTY === MAX_BOT_DIFFICULTY === 'competitive'`, so the badge rests on an
unenforced ordering invariant.** `server/game/BotPolicy.js:69,76`, `server/game/RoomManager.js:140-152`

A freshly constructed `Room` sets `botDifficulty = DEFAULT_BOT_DIFFICULTY` and builds its policy
from it, so `botPolicy.difficulty === 'competitive'` — indistinguishable from a host's explicit
choice — *before* `configureBotPolicyForRoster()` or `setForceMaxBots()` has ever run. The feed's
`maxBots` check cannot tell the two apart.

Today this is safe: `start_game` (index.js:1748) and `host_rematch` (index.js:2156) both call
`configureBotsForRoom` and abort on error, and `recordAbandonedGame` requires `room.gameId`, which
only `startGame()` sets. But nothing enforces or tests that ordering. A future game-start path, an
admin/test room, or a refactor that reorders those two calls would badge games nobody opted into —
and this is precisely the failure mode `docs/BOT-DIFFICULTY.md` congratulates itself on having
eliminated ("There is no second field here to disagree, so the label cannot lie"). Here there *is* a
coincidental second value that agrees by accident rather than by construction.

Two options, not mutually exclusive: (a) add a test asserting that a default room which starts a
game records `'adaptive'` and *not* `'competitive'`; (b) record the host's `forceMaxBots` intent
explicitly rather than inferring it from a tier id that doubles as the default.

**S3. The docs' central claim is factually wrong: difficulty is already shown to viewers elsewhere.**
`CLAUDE.md` (new `set_max_bots` bullet), `docs/BOT-DIFFICULTY.md` ("What a viewer is shown")

"the one difficulty fact a finished game ever shows a viewer" is contradicted by untouched code.
`getDealStrengthStats` (`server/db.js:2306-2307`, `2324-2325`) splits rounds on
`bot_difficulty <> 'competitive'`, `/api/stats/:username/hand-strength` ships that split
unauthenticated keyed only on username, and `StatsV2.jsx:790` renders it as a literal **"Easy bots"**
chip. CLAUDE.md's own adjacent hand-strength bullet already describes this.

Narrow the claim rather than delete it — it is still true at the per-game, tier-named level. E.g.
"…is the only *per-game* difficulty label a finished game shows a viewer; the hand-strength stats'
'Easy bots' scope also reflects difficulty, but as an aggregate across rounds, never naming a game
or a tier."

**S4. The migration itself is untested, and the repo has precedent for testing exactly this.**
`server/db.js:623-638` — criticality 7

`server/test/publicRankMigration.test.js` already builds a legacy database on disk, requires
`db.js` against it, and asserts the migrated column plus a real write both land;
`gamelogMigration.test.js` does the same for the ML store and CLAUDE.md documents why. No equivalent
exists here, and per S1 the failure mode is now a rolled-back transaction rather than a missing
badge. Mirror `publicRankMigration.test.js`: legacy `game_history` without the column → require
`db.js` → `saveGameHistory({ botDifficulty: 'competitive' })` → assert the value persists.

**S5. None of the five new write sites is exercised end-to-end.** `server/index.js:273, 851, 1208,
1777, 2183` — criticality 7

No test proves a real game records the room's live `botPolicy.difficulty`, and in particular none
proves a **normal game records `'adaptive'` and not `'competitive'`** — the assertion that would
catch S2. `recordAbandonedGame` is documented "Never throws" and swallows this write's errors, which
is the exact silent-failure shape the repo's other migration test exists to guard against. The
difficulty-*selection* logic is well covered at the Room level in `botDifficulty.test.js:215-301`;
the gap is the plumbing from `Room` into the DB write. Cheapest meaningful test: build a `Room`,
call `recordAbandonedGame` directly (no socket harness needed), and assert
`game_history.bot_difficulty` matches `room.botPolicy.difficulty` for both a default room and a
`forceMaxBots` room.

**S6. No coverage of `maxBots` on abandoned games.** `server/test/activityFeed.test.js` —
criticality 5

All five new tests use `status: 'completed'`, yet `recordAbandonedGame` is one of the five writers
and the file's own header explains that abandoned games surface under the "Rage quits" filter. Add a
case: abandoned + `'competitive'` + bot participants → `getActivityFeed({ includeStatus:
['abandoned'] })` returns `maxBots: true`.

**S7. Goal gap — the badge is absent from the one screen where the achievement happens.**
`client/src/components/GameRoom.jsx:1125`

The PR's stated purpose is that beating max bots "is worth showing off." The in-game post-game
screen is `GameOverV2`, and it renders no chip. (`GameRoom.jsx:10` imports `ScoreDialog` but never
renders it — pre-existing dead import; `ScoreDialog` is only mounted by `Lobby.jsx`.) The client
already has `gameState.forceMaxBots` — it is passed to `WaitingRoomV2` at `GameRoom.jsx:1154` — so
the data is in hand. As shipped, a player finishing a max-bots game sees nothing until they go back
to the home screen and find the game in Recent.

**S8. `MaxBotsChip`'s `style` prop is speculative and unused.**
`client/src/components/tableV2/MaxBotsChip.jsx:21,39`

All three call sites (`ScoreDialog.jsx:74`, `ActivityFeedV2.jsx:229`, `HomeScreenV2.jsx:404`) render
a bare `<MaxBotsChip />`. No other `tableV2/` component uses a `{ style }` passthrough, so it is not
inherited convention either. Drop it until a second caller needs it.

**S9. `ScoreDialog` bypasses the barrel it was just added to.** `client/src/components/ScoreDialog.jsx:3`

`MaxBotsChip` is exported from `tableV2/index.js:16`, but `ScoreDialog` imports it by direct path.
Every other top-level `components/*.jsx` consumer of a barrel-exported `tableV2` component
(`Stats`, `ActivityFeed`, `GameRoom`, `Leaderboard`, `Lobby`, `Training`, `GameReview`) goes through
the barrel; the two existing direct-path exceptions (`HowToPlay` → `PileCardGlyph`,
`Login`/`Profile` → `LoginV2`) are legitimate because those symbols are *not* in the barrel. Use
`import { MaxBotsChip } from './tableV2';`.

**S10. Four near-identical chip style objects now sit in two files.**
`client/src/components/tableV2/ActivityFeedV2.jsx:216,220,225` + `MaxBotsChip.jsx:26-40`

The mode chip, QUIT, PRIVATE and MAX BOTS all repeat `fontSize: 10, fontWeight: 800,
letterSpacing: .6, padding: '3px 8px', borderRadius: 7, whiteSpace: 'nowrap'`, varying only
background/border/colour and label. This PR is the moment the pattern crosses from "three inline
spans in one file" to "a component plus three inline spans" — the worst of both. A single
`<Chip tone={...}>` primitive would make `MaxBotsChip` a one-liner and let the badge row stay
visually consistent by construction.

**S11. The same rationale is restated in full in roughly five places.** `CLAUDE.md:585-591`,
`docs/BOT-DIFFICULTY.md:196-239`, `server/db.js:606-621`, `server/db.js:2149-2155`,
`server/db.js:2538-2545`, `MaxBotsChip.jsx:3-20`

Each independently re-derives the same three facts (only ceiling-tier + a seated bot is badged;
adaptive is hidden because the feed is public; NULL is never backfilled). This repo's convention
elsewhere is one canonical doc plus a short pointer — that is how `BotPolicy.js` and
`DealStrength.js` are documented. `MaxBotsChip.jsx` points at the doc but still restates everything
above the pointer, and neither `db.js` block points at the doc at all. Five prose copies is five
things to reconcile the first time this rule changes.

This repo genuinely does write long explanatory comments, so this is a judgement call rather than a
convention violation — but the multiplier here is unusually high for a boolean.

**S12. `maxBots` is the first top-level camelCase key in the feed payload.** `server/db.js:2545`

Before this PR the `/api/activity` game object was entirely snake_case at the top level, including
the one pre-existing *computed* field, `event_count` (`db.js:2509`) — which was evidently named to
match the raw columns rather than `eventCount`. Nested `participants[]` are already camelCase, so
the payload had a coherent top-level-snake / nested-camel split that `maxBots` breaks. Either rename
to `max_bots`, or adopt camelCase for derived fields deliberately and rename `event_count` too.
Cheap now, a compatibility question later.

**S13. `getDealStrengthStats` still hardcodes `'competitive'` in SQL.** `server/db.js:2306-2307,
2324-2325`

Pre-existing and out of scope, but this PR introduces `MAX_BOT_DIFFICULTY_ID` precisely so the
ceiling has one name — and leaves a third unlinked copy of the literal two hundred lines above the
new constant. Worth a follow-up so a retune moves all of them.

### Nits

**N1.** `server/db.js:2149-2155` — the `MAX_BOT_DIFFICULTY_ID` comment says it is pinned "by the
same test" as `BOT_DIFFICULTY_IDS` above it. They are two separate test cases
(`botDifficulty.test.js:434` and `:442`). "by a sibling test" would be accurate.

**N2.** `server/index.js:1772-1776` — "Read off the policy the room snapshotted in `startGame()`".
The policy is snapshotted by `configureBotsForRoom` → `configureBotPolicyForRoster` → `refreshBotPolicy`,
which run *before* `room.startGame()`; `startGame()` itself only re-refreshes when the tier is
`adaptive` (`RoomManager.js:767-769`). The substantive point of the comment (read the policy, not
`forceMaxBots`) is right; the attribution is not.

**N3.** `client/src/components/ScoreDialog.jsx:69-71` — "Only ever set for a finished game opened
from the activity feed." The `/activity` page expands standings in place and never mounts
`ScoreDialog` — `ActivityFeedV2.jsx:14-15` says so explicitly. The dialog is opened only from the
home screen's Recent list (`Lobby.jsx:162-193`), which happens to be fed by `/api/activity`. The
pre-existing comment directly above uses the same loose vocabulary, so this is consistent with the
file — but the PR body and `docs/BOT-DIFFICULTY.md:200` both say "the score dialog *they* open,"
and only one of the two opens it.

**N4.** `bot_difficulty TEXT` has no `CHECK` constraint, though `status` in the same `CREATE TABLE`
(`db.js:237`) does and the valid set is a known four-element enum. Nothing at the DB layer bounds
the column.

**N5.** Redundant and inconsistent boolean coercion: `Lobby.jsx:184` and `ActivityFeedV2.jsx:103`
both do `!!game.maxBots` on a field the server already computes as a real boolean, while
`HomeScreenV2.jsx:404` consumes it bare. Harmless, but the three sites weren't written against one
understanding of the type. Pick one.

### Questions

**Q1.** Max difficulty **suspends placement for everyone at the table**
(`docs/BOT-DIFFICULTY.md:185-192`), and the toggle is deliberately quiet and host-only. The badge is
now the first *public* signal of a setting that costs non-host players placement progress they never
opted into — and they only see it after the fact, in the feed. Should the waiting room show
non-hosts that max bots is on, given this PR makes the consequence publicly legible?

**Q2.** Should *abandoned* games be badged? They are today, if bots were seated —
`recordAbandonedGame` writes the tier and the "Rage quits" filter shows them. A rage quit wearing a
gold "worth showing off" chip alongside the warm-red QUIT is at least worth an explicit decision
rather than a side effect.

**Q3.** The PR argues from a privacy premise that is already broken elsewhere in the app.
`round_stats.bot_temperature` — the exact continuous hidden dial the docs say must never be shown —
is returned raw by `GET /api/stats/:username/rounds` (`db.js:1552` `SELECT *` →
`index.js:3109-3124`), unauthenticated, for any username. And
`GET /api/debug/game/:gameId` (`index.js:2489`, self-labelled "TEMPORARY - REMOVE AFTER DEBUGGING")
returns the entire raw `game_history` row, now including `bot_difficulty`. Neither is a regression
from this PR, but both contradict `docs/BOT-DIFFICULTY.md:167-168` ("Seat payloads … expose neither
the hidden opponent rating nor the exact Adaptive temperature"). Follow-up ticket?

**Q4.** Related pre-existing bug worth a ticket: `getDealStrengthStats`'s "Easy bots" scope is
`bot_difficulty <> 'competitive'`. Since `adaptive` became the default, essentially *every* normal
game classifies as "weakened" — so `vsBots` vs `vsCasualBots` may no longer mean what CLAUDE.md's
hand-strength bullet says it means ("rounds against deliberately weakened bots"). Did the semantics
drift when adaptive shipped?

**Q5. The "four humans are never badged" guarantee is not absolute — is the exception intended?**
`server/db.js:2415` (`ON CONFLICT(game_id, username)`), `server/index.js:1212-1230`

`saveGameParticipant` keys its upsert on `(game_id, username)`. When a human quits mid-game they are
swapped for a bot with a *different* name, so a completed game's participant write **inserts a new
row** for the substitute rather than updating the departed human's (whose row is left stale with
`final_placement = NULL`). A `forceMaxBots` room that started with four humans therefore *does* earn
the badge once someone quits and a bot finishes for them — `participants.some(p => p.isBot)` picks
up the substitute's row.

Arguably this is correct: a max-difficulty bot really did play. But it is exactly the case the new
test `a max-difficulty game with no bots in it is not badged` is written to exclude, and both
`docs/BOT-DIFFICULTY.md` and the `getActivityFeed` comment state the "nothing to apply it to"
guarantee absolutely. Either the docs should acknowledge the substitution case, or the guarantee
should be phrased as "no bot ever sat at this table" rather than "the game started with four
humans." (The abandoned-game path is unaffected — `describeParticipants()` correctly reattributes a
bot-replaced seat to the departed human, so an abandoned game is *not* falsely badged.)

## Correctness

**No logic defects found in the diff.** Every code path was traced end-to-end rather than inferred
from the diff. Verified and sound:

- **The `'competitive'` ambiguity is not exploitable today.** `configureBotPolicyForRoster()`
  (`RoomManager.js:1079-1089`) *unconditionally* overwrites `botDifficulty` with either
  `MAX_BOT_DIFFICULTY` or `'adaptive'` — it can never leave the constructor's default in place. Both
  paths that can start or resume a game (`start_game` at `index.js:1748`, `host_rematch` at
  `index.js:2156`) call `configureBotsForRoom` and `return` on `.error` *before* starting, and all
  five write sites run strictly downstream of an already-started game. So `'competitive'` is
  recorded only when `forceMaxBots` was genuinely on. S2 records this as a latent invariant, not a
  live bug.
- **The `BOT_DIFFICULTY` env default in `createBotPolicy` (`BotPolicy.js:292`) is dead in
  production** — every live call site passes `difficulty` explicitly. Worth a pinning test or a
  comment, since a future caller that omits it would resurrect exactly the ambiguity S2 describes.
- **Rematch and lobby-restart chains are correct.** `host_rematch` re-runs `configureBotsForRoom`
  before writing the new row, `startRematch()` re-runs `configureBotPolicyForRoster()` (redundant but
  idempotent), and `forceMaxBots` persists on the room across the boundary because it can only be
  toggled in `waiting`.

Verified and sound:

- **Placeholder/binding arity** in the rewritten `saveGameHistory` (`db.js:2375-2393`): 13 INSERT +
  8 `DO UPDATE` placeholders against a 21-element bound array. Correct.
- **`COALESCE(?, bot_difficulty)`** cannot clobber a good value with NULL, and the destructuring
  default `botDifficulty = null` turns an omitted key into a real NULL rather than `undefined`.
- **`participants.some(p => p.isBot)`** — `isBot` arrives from SQLite's `json_object('isBot',
  gp.is_bot)` as integer 0/1; the truthiness check is correct.
- **`maxBots` is always a real boolean**, never `undefined`, because the `===` short-circuits to
  `false`. The new `assert.strictEqual(..., false)` assertions are therefore meaningful and not
  passing vacuously.
- **NULL rows** compare false against `MAX_BOT_DIFFICULTY_ID`, so pre-migration history is never
  mis-badged. `getActivityFeed` is the only reader of the column.
- **`room.botPolicy` is always initialized** in the `Room` constructor (`RoomManager.js:152`), before
  `gameId` can exist, so none of the five new call sites can throw on `.difficulty`.
- **Rolling-deploy compatibility both ways.** Old-opens/new-finishes heals via `COALESCE` (and is
  tested). New-opens/old-finishes is also safe: the old `DO UPDATE` never names the column, so
  SQLite leaves it untouched.
- **Migration ordering within `initDb`.** The new `PRAGMA` block sits inside the same
  `db.serialize()` as the `CREATE TABLE`, so the PRAGMA reads a table that exists, and
  `columns.length > 0` correctly no-ops on a fresh database (where the CREATE already included the
  column). The block matches the four existing blocks byte-for-byte in shape.
- **`maxBots` reaches every surface it claims to, with no dual-path risk.** `/api/activity` returns
  `getActivityFeed`'s rows verbatim; `Lobby.jsx:247` feeds `HomeScreenV2`'s Recent list from that
  same endpoint, and `Lobby.handleGameClick` forwards the same raw field into `ScoreDialog`.
  `ActivityFeedV2` draws the chip on its own card and never mounts `ScoreDialog`.
- **Layout degrades correctly.** `HomeScreenV2`'s Recent row keeps the chip outside the
  `flex:1 min-width:0` truncating block with `flexShrink:0`, so a long winner name ellipsises rather
  than pushing the chip out; `ActivityFeedV2`'s `flex-wrap` change is the deliberate, commented fix
  for QUIT + PRIVATE + MAX BOTS at 320px.

Open correctness concerns are **S1** (boot race) and **S2** (the `'competitive'` collision); both
are ordering/lifecycle issues rather than logic errors in the diff itself. **Q5** records a
participant-upsert edge case that makes one documented guarantee non-absolute.

One agent claim I checked and could not confirm: `GameRoom.jsx` does *not* render `ScoreDialog` — the
symbol appears exactly once in that file, on the import line (`GameRoom.jsx:10`), making it a
pre-existing dead import. The live post-game screen is `GameOverV2` (S7).

## Maintainability

## Security

C1 is the finding. Two out-of-scope observations that materially undercut the PR's stated threat
model are recorded as Q3.

Verified sound: `botDifficulty` is fully parameterized in both the INSERT and the `DO UPDATE`; its

## Performance

Nothing significant, checked deliberately rather than assumed.

- `participants.some(...)` runs once per already-fetched row over an at-most-4-element in-memory
  array — ≤80 comparisons per request at the default `limit=20`. No extra queries.
- The CTE and its index usage are unchanged; `page.*` already selected every column, so the new one
  adds roughly 0.6 KB across a 20-row page.
- `ALTER TABLE ADD COLUMN` with no `DEFAULT` and no constraint is metadata-only in SQLite — O(1),
  no table rewrite, no meaningful lock regardless of table size.
- No query filters or sorts on `bot_difficulty`, so no index is warranted and none was added.
- `useTableTheme()` per chip instance is a `useContext` read feeding a `useMemo` keyed on
  `reducedMotion`; ≤20 extra subscriptions per page. Memoizing would add complexity for no gain.

## Data Migration

S1 and S4 above. Verified sound otherwise: the column is additive and nullable with no default, so
`ALTER TABLE ADD COLUMN` is metadata-only; no down migration is needed because the column is safe to
leave in place and safe for old code to ignore; NULL is handled correctly at the only read site; and
both rolling-deploy directions were traced against real code rather than assumed.

## API Contract

S12 (naming) and C1 (payload leak). Backward and forward compatibility are both fine and were
