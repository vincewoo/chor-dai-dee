## Summary

Persists the game-over round-by-round review into a new `game_round_review`
table so the activity feed can render the same `RoundReviewPanel` the players
saw at the table, instead of describing one finished game two different ways.

## How It Works

**Storage.** A new table is declared inline in `initDb()`'s `db.serialize()`
body (`server/db.js:264-282`), between `game_participants` and `game_events`:
`game_id TEXT PRIMARY KEY`, `review TEXT NOT NULL`, `created_at`, and a
`FOREIGN KEY(game_id) REFERENCES game_history(game_id)`. It is a *new table*,
not a new column, so `CREATE TABLE IF NOT EXISTS` is the whole migration — there
is no `ALTER` to lose a boot race with, unlike the `bot_difficulty` precedent
documented at `server/db.js:643-656`.

**Write.** `Room.describeRoundReview(seatNames)`
(`server/game/RoomManager.js:1028-1085`) returns an `Object.create(null)` map
keyed by player name, each entry carrying `avgPercentile`, `dealRank`,
`totalPoints`, `roundsWon` and a `rounds[]` array of per-round
`{round, percentile, tierLabel, rank, points, cardsLeft, won}`. It reads
`roundHistoryBySeat`, which is reset in `startGame()`
(`RoomManager.js:833`) in lockstep with the `gameId` mint — so a rematch cannot
contaminate the previous game's review. The identical object that goes into the
socket payload is `JSON.stringify`'d and inserted verbatim by
`saveGameRoundReview` (`server/db.js:2456-2470`) with
`ON CONFLICT(game_id) DO NOTHING`; an empty review short-circuits before the
insert. Three call sites now cover every terminal path: dragon win
(`server/index.js:899`), normal game over (`:1222`), and — as of `a2d9387` —
`recordAbandonedGame` (`:345`), the last keyed off `describeParticipants()` so a
rage quit's review answers to the seat *owner* rather than the bot sitting in the
seat at teardown.

**Read.** `GET /api/game/:gameId/review` (`server/index.js:2610`) →
`getGameRoundReview` → parsed JSON or `null`, always 200. Deliberately its own
endpoint because `getActivityFeed` selects `page.*`, so anything on
`game_history` ships to every client on every page.

**Client.** `ActivityFeed.jsx` holds a `reviews` map keyed by game id and a
`loadReview` callback fired from the card's expand handler; `ActivityFeedV2.jsx`
adds a `· deals Nth (Mth pct)` suffix to each standings line and renders the
shared `RoundReviewPanel` inside a `stopPropagation` wrapper. Because that panel
carries its own `<button>`, the feed card stopped being a `<button>` and became
a `<div role="button" tabIndex={0}>` with hand-rolled Enter/Space handling.

## Complexity & Risk

**Medium.** Five files, and the schema change itself is the *lowest*-risk part of
the PR: a purely additive table with no backfill, no reversibility problem, and
no lock-a-large-table concern. Verified by execution (below) that it creates
cleanly on an existing database.

The risk is concentrated in three places that are easy to revert individually:
the position of the new `await` relative to the player-facing `game_over` emit;
the hand-rolled keyboard semantics on the converted card; and the client's
three-states-collapsed-into-`null` cache. None of them can corrupt data. All
three are user-visible.

The one structural risk with a long tail is that a username-keyed JSON blob is
now persisted forever, in a codebase whose own CLAUDE.md calls out
username-denormalization as a rename hazard, and with no schema-version stamp
despite the `deal_baseline_version` precedent sitting in the adjacent table.

## Findings

### Critical

**C1. The nested "Round by round" button is keyboard-dead, and Enter/Space on it
collapses the entire feed card.**
`client/src/components/tableV2/ActivityFeedV2.jsx:208-221, 344-355`

The `<button>` → `<div role="button">` change fixed HTML parseability, but the
wrapper only stops **click**:

```jsx
<div onClick={(e) => e.stopPropagation()}>
    <RoundReviewPanel ... />
</div>
```

`keydown` still bubbles from the panel's own `<button>` to the card's
`onKeyDown`, which matches `Enter`/`' '` unconditionally, calls
`e.preventDefault()` — suppressing the click the browser would have synthesized
for the inner button — and toggles `expandedId`.

Verified by execution (headless Chromium 1228 via `playwright-core`, against a
faithful DOM reproduction of the new card structure):

```
--- CASE A: focus the INNER "Round by round" button, press Enter ---
CARD onKeyDown("Enter") -> preventDefault(); expanded=false
inner aria-expanded after Enter = false          <-- inner never toggled

--- CASE B: same, press Space ---
CARD onKeyDown(" ") -> preventDefault(); expanded=true
inner aria-expanded after Space = false          <-- inner never toggled

--- CASE C: MOUSE click the inner button ---
INNER onClick -> panelOpen=true
wrapper stopPropagation(click)
inner aria-expanded after click = true           <-- mouse works
```

So a keyboard user can focus the review toggle but can never open it; both keys
close the card out from under them instead. This directly defeats the change's
own stated justification — *"Keyboard and ARIA behaviour are kept by hand so this
is a change of element, not of affordance."* The affordance did change.

Two fixes, either sufficient for the immediate bug:
- guard the handler with `if (e.target !== e.currentTarget) return;` before the
  key check, or
- add `onKeyDown={(e) => e.stopPropagation()}` to the existing wrapper div
  alongside the `onClick` one.

**The deeper issue is structural and worth fixing properly.** A focusable
`<button>` inside `role="button"` is the same ARIA violation as the
button-in-button it replaced — the parse error went away, the accessibility
error did not (confirmed: both elements are focusable, in DOM order,
`['DIV#card role=button', 'BUTTON#inner role=native']`). And because the
expanded body lives *inside* the role=button element, that element's accessible
name is computed from the entire standings block. The standard shape here is the
disclosure pattern: a `<button>` on the header row only, with the expanded body
as its **sibling**, referenced by `aria-controls`. That removes the nesting, the
name-computation problem and the bubbling bug at once, and lets the header go
back to being a real `<button>` (which is also where `disabled={!canExpand}`
belonged).

*Not* a regression, verified: the focus ring survives the conversion —
`div[tabindex="0"]` still gets `outline-style: auto` and matches
`:focus-visible` (CASE E).

**C2. The review write blocks the player-facing `game_over` / `dragon_win` emit —
the only write in these handlers placed before it.**
`server/index.js:1218-1231` (game over), `:897-908` (dragon)

```js
try {
    await saveGameRoundReview(room.gameId, gameResults.roundReview);
} catch (e) { console.error('Failed to save round review:', e); }

room.lastGameResults = gameResults;
room.gameState = 'finished';

io.to(roomId).emit('game_over', gameResults);   // <-- gated by the write above
```

Every sibling persistence call in the same handler — `saveGameHistory`,
`saveGameParticipant`, `saveBotCalibration` — is deliberately placed *after* the
emit, each in its own try/catch, precisely so a database write cannot delay four
players' scoreboards. `db.js` sets `PRAGMA busy_timeout = 5000`
(`server/db.js:52`), and the server can end several games concurrently on a
single shared sqlite3 connection, so a contended write can stall the emit for up
to five seconds.

Nothing in the emitted payload depends on the write: `gameResults.roundReview` is
already fully computed in memory on the line above. The PR's own comment ("a
summary is not worth failing a game over") states exactly the right intent — the
placement just doesn't deliver it.

Notably `recordAbandonedGame` (the second commit) **gets this right**: its
`saveGameRoundReview` runs after the `withTransaction` block commits. Make the
two new call sites match.

Fix: move both calls below their `io.to(roomId).emit(...)` line, or drop the
`await` in favour of a fire-and-forget `.catch(...)`.

**C3. A failed review fetch permanently wedges that card, and is indistinguishable
from "this game has no review".**
`client/src/components/ActivityFeed.jsx:62-75`

```js
const loadReview = useCallback(async (gameId) => {
    if (!gameId || reviews[gameId] !== undefined) return;
    setReviews(prev => ({ ...prev, [gameId]: null }));   // in-flight marker
    try {
        const response = await fetch(`${serverUrl}/api/game/${gameId}/review`);
        if (!response.ok) return;                         // leaves the entry at null
        const data = await response.json();
        setReviews(prev => ({ ...prev, [gameId]: data.review || null }));
    } catch (err) {
        console.error('Error fetching round review:', err);  // also leaves it at null
    }
}, [serverUrl, reviews]);
```

The in-flight sentinel is `null` — the *same* value that means "this game
predates the feature". On a non-2xx or a thrown fetch, the entry is never moved
off `null`, and the guard `reviews[gameId] !== undefined` is then permanently
true: collapsing and re-expanding the card never retries. Only a full remount
(navigating away from the feed and back) clears it.

Three distinct states — loading, failed, legitimately absent — collapse into one
that both `RoundReviewPanel` (`if (!roundReview || rounds.length === 0) return
null`) and the deal-strength suffix render as silently nothing. A one-second
network blip permanently hides a working feature for the rest of the session,
with no way for the user to tell it is a bug.

Fix: use a distinct sentinel for in-flight (or track in-flight ids in a ref), and
on failure either delete the key or store an error marker so the next expand
retries.

### Suggestions

**S1. A rename orphans every one of that player's stored reviews.** *(verified by
execution)*
`server/db.js:3044-3055` (`renameUser`) vs `server/db.js:2456`

`renameUser` updates `users`, `game_history.winner_username`,
`game_participants.username` and `username_history`. It does not — and cannot,
with the current design — touch `game_round_review`, whose usernames are the
**keys of a JSON blob**. `ActivityFeedV2` looks the review up by
`p.username`, which comes from the *updated* `game_participants` row, against a
review still keyed on the pre-rename name:

```
BEFORE rename -> participants[0].username: Alice
BEFORE rename -> review keys: [ 'Alice' ]
AFTER  rename -> participants[0].username: Alicia
AFTER  rename -> review keys (unchanged):  [ 'Alice' ]
AFTER  rename -> review[NEW username]:     undefined
```

The user-visible symptom is worse than "nothing renders": `RoundReviewPanel`
derives its **columns** from the union of all review entries (which still exist)
but its **rows** from `c.participants`, so the panel opens to a complete grid of
dashes with a `–` total on every line. The deal-strength suffix disappears from
every standings row too.

This is precisely the class of bug CLAUDE.md documents for
`game_history`/`game_participants`. Three honest options — pick one
deliberately:
1. key the review on **seat index** (like the ML game log) or `user_id`, and
   resolve names at read time — the design the rest of the schema already uses;
2. backfill the blob inside `renameUser`'s transaction (a JSON rewrite, ugly but
   contained);
3. accept it and say so in the CLAUDE.md sentence that currently claims
   `game_history` and `game_participants` are "the only two places in the schema"
   storing a username — that claim is now false, see D1.

**S2. The write is a bare `db.run` outside `withTransaction`, on the shared
connection.** `server/db.js:2456-2470`

`db.js`'s own comment (lines 61-69) documents the hazard verbatim: *"writes
issued elsewhere while a transaction is open ride along in that transaction and
would be lost on rollback."* `saveGameRoundReview` is not queued through
`transactionQueue`, so if it executes while any other room's `withTransaction`
block is open (round stats, final stats, game history — all reachable
concurrently), it joins that transaction. If that transaction later rolls back,
the review row vanishes **after `saveGameRoundReview` already resolved
successfully** — nothing throws, nothing logs, nothing retries.

Moving the call after the game-over emit (C2) does not fix this on its own;
folding it into the same `withTransaction` block as `saveGameHistory` would fix
both this and S3.

**S3. The FK parent row is written *after* the child, on every game-over path.**
`server/index.js:1222` vs `:1285`; `:899` vs `:917`

`game_round_review` declares `FOREIGN KEY(game_id) REFERENCES
game_history(game_id)`, but the review is inserted before `saveGameHistory` ever
runs. This is silently tolerated only because `PRAGMA foreign_keys` is never
enabled anywhere in the codebase — the constraint is decorative. It was
confirmed by execution that with `foreign_keys = ON` and the current call order,
the insert throws `SQLITE_CONSTRAINT: FOREIGN KEY constraint failed` **every
time, not intermittently** — and the try/catch would swallow it, so a future
"harden the DB" change would silently stop recording reviews forever.
(`game_history.game_id` is `TEXT PRIMARY KEY`, so there is no "foreign key
mismatch" risk — only ordering.)

Either reorder (which C2's fix mostly achieves) or drop the FK clause and say in
the comment that it isn't an enforced invariant.

**S4. The persisted blob has no schema/version stamp, against local precedent.**
`server/db.js:264-282`

Everything in the blob — `avgPercentile`, `dealRank`, per-round `percentile` and
`tierLabel` — is derived from `DealStrength`, which already solved exactly this
problem for `round_stats` via `BASELINE_VERSION` / `deal_baseline_version`
(`server/db.js:179`), with a comment saying *"Bump when the formula, the tier
cutoffs, or the baseline table below change, so rows recorded under an old
baseline stay interpretable."* Reviews are persisted verbatim and forever; when
the formula or the shape changes, old rows will be re-read under the new
interpretation with nothing to distinguish them. Add a `review_version` column
(or store `DealStrength.BASELINE_VERSION` alongside).

**S5. `/api/game/:gameId/review` collides with the existing `review` noun.**
`server/index.js:2610` vs `:3390`, `:3424`

`/api/review/:gameId` and `/api/review/examples/:username` already exist and mean
something entirely different (move-quality grading from `MoveReview.js`). The new
route introduces a top-level `/api/game` noun for exactly one endpoint, gives
"review" a second meaning, and is registered *above* the `// Activity Feed
Routes` comment block even though the activity feed is its only caller. No
routing shadowing (verified against the full route list), so this is naming, not
breakage — but `/api/activity/:gameId/round-review` inside the feed block would
say what it is. Every other nested resource in this app follows
`/api/<noun>/<id>/<sub>` (`/api/stats/:username/tier3`,
`/api/account/:userId/password`).

**S6. Failure logs carry no `gameId`.** `server/index.js:347, 901, 1224`

`console.error('Failed to save round review:', e)` cannot be attributed to a game
in Fly logs. The read path already does this correctly —
`console.error('Malformed round review for', gameId, e)` (`server/db.js:2488`).
The sibling history-save logs share the omission, so this matches (weak) local
convention rather than breaking it; still worth adding, since there is no metrics
or alerting anywhere in this codebase and grepping logs is the only way anyone
would ever notice review recording had silently stopped.

**S7. Duplicated handler bodies and duplicated deal-strength formatting.**
`ActivityFeedV2.jsx:208-221`, `:40-44`, `:330-332`

The four-line expand action (compute `next`, `setExpandedId`, conditionally
`onExpandGame`) is written out verbatim in both `onClick` and `onKeyDown`.
`HomeScreenV2.jsx:203-210` already establishes the local pattern of calling one
shared action from both. Separately, `ordinalSuffix` is defined identically in
`ActivityFeedV2.jsx` and `GameOverV2.jsx:188-192`, and this PR adds a *second*
independent composition of the same `dealRank`/`avgPercentile` pair with drifting
wording ("deals Nth (Mth pct)" here vs "Deal strength: Nth" there).
`RoundReviewPanel` is already shared between these two screens specifically so
the deal-strength read cannot drift; the one-line summary above it deserves the
same treatment.

**S8. Client cache hygiene.** `ActivityFeed.jsx:62-75`

`reviews` is in `loadReview`'s dependency array, so the callback's identity
changes twice per expand and re-renders the whole card list (cheap at 20 cards,
but avoidable — use the functional form for the presence check, or a ref). The
map is also never cleared on filter change or pagination and has no eviction, so
it grows for the life of the mount. Measured payloads are 4.0 KB at 10 rounds,
7.8 KB at 20, 11.5 KB at 30 — so the PR's "a few KB" holds for typical games but
understates the tail.

**S9. No cache headers on an immutable resource.** `server/index.js:2610`

A finished game's review is write-once (`ON CONFLICT DO NOTHING`) and can never
change, which makes it one of the few genuinely `Cache-Control: immutable`
responses in this app. No other endpoint sets cache headers either, so this is an
opportunity rather than an inconsistency.

### Questions

- **Q1.** Was keying the blob on **username** rather than seat index / `user_id` a
  deliberate call (S1)? The ML game log is explicitly keyed on seat "since socket
  ids change mid-game", and `describeParticipants()` already returns seats in
  `this.players` order, so the seat-indexed version would be a small change and
  would make the rename question disappear.
- **Q2.** `GET /api/game/:gameId/review` returns `{review: null}` both for a game
  with no stored review and for a `gameId` that never existed. Deliberate? Every
  other endpoint that can be asked about a nonexistent resource 404s
  (`/api/stats/:username`). Nothing needs the distinction today.
- **Q3.** `game_round_review` has no retention or archival path, and nothing ever
  deletes from `game_history` either — so rows accumulate at ~5-12 KB per game
  forever. Fine at current scale (~5-12 MB per 1000 games); is that the intended
  steady state?

## Correctness

Verified sound, no findings beyond C1-C3 and S1-S3:

- **Write-path completeness is now correct.** All three terminal paths write:
  `game_over` (`index.js:1222`), `dragon_win` (`:899`), and `recordAbandonedGame`
  (`:345`, added by `a2d9387`). Before that second commit the "Rage quits" tab
  was the one place a card could expand to nothing.
- **`room.gameId` is still the right id at the write.** `gameId` is re-minted
  only in `resetForNewGame`/`startRematch`, both gated on
  `gameState === 'finished'` and both client-triggered after `game_over` is
  received. `roundHistoryBySeat` resets in the same place
  (`RoomManager.js:833`), so no cross-game contamination is possible.
- **The abandoned path keys correctly.** `describeParticipants()` is
  `this.players.map(...)` (`RoomManager.js:2286`), preserving seat order, so
  `seats.map(s => s.username)` aligns index-for-index with
  `roundHistoryBySeat`. Owner names, not `Bot (Alice)`.
- **The try/catch does catch the synchronous throw.** A `JSON.stringify` throw
  inside the Promise executor becomes a rejection and is caught (verified by
  execution). Moot in practice — `describeRoundReview` builds a flat object of
  primitives.
- **No infinite render loop** from `loadReview`'s churning identity: it is
  referenced only from event handlers, never from a `useEffect`.
- **`c.id` is `g.game_id`** (`ActivityFeedV2.jsx:102`), matching what the
  endpoint expects.
- **The empty-review guard is correct** and `Object.keys` works on the
  null-prototype object.

## Maintainability

See S4 (no version stamp), S5 (endpoint naming), S7 (duplicated handler bodies
and `ordinalSuffix`/deal-string), S8 (cache hygiene), N1.

Explicitly evaluated and **rejected** as findings:
- **`game_events` was not the right home.** It is append-only, many-rows-per-game,
  no unique constraint, read in full per game; this is one upsert-once summary
  keyed by game id. Reusing it would mean adding a
  `UNIQUE(game_id, event_type)` and an `event_type`-filtered read path for no
  benefit. The `db.js` comment already reasons this through honestly.
- **Prop drilling `reviews`/`onExpandGame`** matches how `ActivityFeedV2` already
  receives `games`/`filters`/`loading`; the cache belongs in the container.
- **`role="button"` convention** — `HomeScreenV2.jsx` is the only other instance
  and is a good precedent, not a contradicted one.
- **Comment density** matches the house style of long "why, not what" comments.

## Documentation

**D1. CLAUDE.md's username claim is now false — highest-value doc fix.**
CLAUDE.md, `game_history` bullet under "Activity Feed Tables":

> Note both this table and `game_participants` store the **username**, not just
> the id — they are the only two places in the schema that do, and therefore the
> only two a rename has to backfill…

`game_round_review` now stores usernames too, as its JSON object keys, and is
**not** backfilled (S1). Whether that is a bug or an accepted limitation, the
sentence has to stop asserting something untrue — this is the note a future
reader will rely on when adding the next table.

**D2. The new endpoint is undocumented.** There is no "Activity Feed" subsection
under "REST API Endpoints" at all (`/api/activity` is missing too — pre-existing).
Add one covering both, noting the 200-with-null contract and that it is
unauthenticated like the rest of the feed reads.

**D3. The new table is undocumented.** Belongs under "Activity Feed Tables" after
`game_participants`: one row per game, JSON keyed by username, covers bots and
guests (which is why `round_stats` cannot serve it), first-write-wins.

**D4. "exactly one place" / "one caller" is stale in two files.** CLAUDE.md's
`DealStrength.js` bullet says the per-round `rank` "surfaces in exactly one
place: the game-over screen", and `docs/HAND-STRENGTH-STATS.md` says
`describeRoundReview()` "has exactly one caller — the game-over handler". Both
are now wrong: three callers (game over, dragon win, abandon), and the data is
persisted and served indefinitely by a public endpoint.
`docs/HAND-STRENGTH-STATS.md`'s "Where a player sees this — Two places" section
needs a third entry. The *substance* of the warning still holds — the leak
boundary is mid-round vs. post-game, and this PR respects it — but the prose
should say that rather than counting callers.

Checked and **not** a gap: retention. `game_round_review` inherits the same
undocumented-but-permanent lifecycle as `game_history` and `game_participants`,
none of which are ever pruned (`sweepAbandonedGames` only updates `status`).
Inventing a retention note for this one table alone would be inconsistent.

## Security

**No actionable findings.** Verified live against a scratch database on port 3999.

- The query is fully parameterized. `'` OR 1=1--`, `%00`, a 5000-char id and
  URL-encoded traversal all return `200 {"review":null}` with no error and no
  stack trace.
- **No mid-round leak.** CLAUDE.md's rule that `DealStrength.rank` "must never
  reach a client mid-round" is respected: all three write paths are reachable
  only once the game has concluded, `game_id` is a PRIMARY KEY with
  `ON CONFLICT DO NOTHING`, and a rematch always mints a fresh `gameId` — so no
  row can exist for a game that can still receive plays.
- **No new exposure.** The identical payload was already broadcast to all four
  seats over the socket at game end, and `/api/activity` already publishes every
  game's `game_id`, participants, scores and placements to anyone ("full
  transparency… No filtering by `is_public` for now"). Game ids need not even be
  guessed — they are already listed.
- **No prototype pollution.** `validateUsername` does permit `__proto__`, but
  `describeRoundReview` builds on `Object.create(null)` *specifically* for that
  reason (comment at `RoomManager.js:1029-1035`), and `JSON.parse` creates
  `"__proto__"` as an own data property, so the client read is safe too.
- The 500 handler leaks nothing.

Residual, pre-existing and not introduced here: there is no rate limiting
anywhere in the server, so this is one more unauthenticated, unthrottled read
endpoint on an already fully-scrapeable feed.

## Data Migration

**The migration is correct. This was the biggest question going in and it comes
back clean.** Verified by execution, not inference:

```
### STEP 1: create DB with origin/main's db.js
  game* tables: game_history, game_participants, game_events
  HAS game_round_review: false

### STEP 2: open the SAME file with the BRANCH's db.js and write+read
  round-trip on a pre-existing DB: {"Alice":{"avgPercentile":55,"dealRank":1,...}}
```

A database built from `origin/main`'s schema, reopened with the branch's
`db.js`, gains the table and round-trips a real write. `initDb()` runs on every
process start via the sqlite3 open callback, and `CREATE TABLE IF NOT EXISTS` is
a no-op only for tables that already exist — a new one is created.

**The boot-race precedent does not apply.** The hazard documented at
`server/db.js:643-656` is specific to a *callback-scheduled `ALTER`* landing at
the back of sqlite3's queue after the server has started accepting traffic. This
statement is queued **inline** in the `db.serialize()` body, so it is ordered
against the `CREATE TABLE`s around it and every later write, exactly as that
comment prescribes.

A residual race does exist and is reproducible only at the extreme:

```
### STEP 3: BOOT RACE — write issued at process.nextTick, no await
  write at nextTick THREW: SQLITE_ERROR: no such table: game_round_review
```

This is **unreachable in production**: `saveGameRoundReview` is only called from
a game-over handler, rooms are in-memory and lost on restart, so no game can end
within microseconds of `require('./db')`. Both call sites are guarded, so it
would fail soft anyway. Worth recording as a systemic gap — `db.js` exports no
readiness signal (`grep dbReady` finds nothing), so any future write path added
nearer to boot inherits it.

Also verified:
- **UPSERT is supported.** sqlite3 5.1.7 bundles SQLite 3.44.2, well above the
  3.24 minimum; `ON CONFLICT DO NOTHING` was executed directly and behaves as
  intended.
- **`game_history.game_id` is `TEXT PRIMARY KEY`**, so the FK has no "foreign key
  mismatch" risk — only the ordering problem in S3.
- **Rollback is safe.** Purely additive; rolling back leaves an unread table.
- **No orphaning path today.** No `DELETE FROM game_history` or
  `DROP TABLE game_history` anywhere in `server/`; `sweepAbandonedGames` only
  updates `status`. The `gamelog:archive` tooling operates on the separate
  `gamelog.sqlite` and cannot touch this table. No `ON DELETE CASCADE` is
  declared, so a future purge/GDPR-delete path would orphan silently.

## Reliability

Covered in C2, C3, S2, S3, S6.

Verified sound:
- **Re-entrancy is safe.** All reconnect paths re-emit from the cached
  `room.lastGameResults` and never re-run game-over logic, and
  `room._abandonRecorded` plus `IN_PLAY_STATES` (excluding `'finished'`) prevent
  an abandon racing a real game over. `ON CONFLICT DO NOTHING` is good hygiene
  for an edge case rather than something today's code exercises.
- **Abandoned games are handled**, and `RoundReviewPanel` renders a partial
  review correctly — it derives its round list from the union of whatever
  `rounds` arrays are present rather than assuming a fixed count.
- A genuine server crash mid-game yields no review, consistent with
  `game_history`/`game_participants` themselves, which also live in memory until
  the game ends.

Lower-severity, not called out above: the client fetch has no `AbortController`
or timeout. Harmless today (there is no loading UI to unstick, and React 19
dropped the unmount-setState warning), but it should land alongside any fix to
C3.
