# Review: PR #158 - fix(v2): keep the felt backdrop off the box that scrolls

**PR**: https://github.com/vincewoo/chor-dai-dee/pull/158
**Author**: @julo15 (Julian Lo)
**Branch**: `julo/mobile-scroll-bg-fixes` → `main`
**Review round**: 1
**Date reviewed**: 2026-08-07

## Summary

Fixes two mobile UI bugs with one structural change: a horizontal scroll on the
Create Game / waiting room screen, and a visible background-colour seam appearing
one viewport down on every scrolling v2 screen. A new shared
`client/src/components/tableV2/ScreenShell.jsx` splits the backdrop-carrying box
from the scrolling box, and ten screens are converted onto it.

## How It Works

**The bug.** Every v2 screen painted its felt backdrop onto the same element that
scrolled. Concretely, each screen's root was
`relative h-full w-full overflow-y-auto overflow-x-hidden` with
`style={{ background: surface.base }}` (the `FELT_BASE` radial gradient from
`theme/tableTheme.js`), plus three `position: absolute` decorative layers as
direct children — an `inset-0` vignette tint, a 520x340 accent glow at
`top: -140px`, and two `SuitWatermark`s — and then the real content in a
`relative z-10 … min-h-full` div.

That root is one viewport tall (`h-full`), but its content is `min-h-full` and
free to be taller. A scroll container's background *positioning* area is its
padding box (one viewport) while its background *painting* area covers the whole
scrollable overflow region, and `background-repeat` defaults to `repeat` — so a
sized gradient tiles a second copy of itself past one viewport. The `inset-0`
tint, being one viewport tall too, simply stops on the same line. Both land
together, drawing a hard horizontal seam. The X-axis symptom is the same mistake:
the glow (520px) and the watermarks (`left: -46`, `right: -52`) bleed past both
edges by design, and on a scroller that bleed is *scrollable* rather than clipped.

**The fix.** `ScreenShell` renders:

```jsx
<div className={`overflow-hidden ${className}`} style={style}>
    {backdrop}
    <div className="relative z-10 h-full w-full overflow-y-auto overflow-x-hidden">
        {children}
    </div>
</div>
```

The root keeps the base gradient and never scrolls, so its background is always
exactly one screen. `overflow-hidden` on it clips the horizontal bleed
structurally, replacing the per-screen `overflow-x-hidden` each new screen had to
remember. The companion `ScreenBackdrop` export packages the tint + glow +
watermark trio; screens pass only `tint`, `soft`, an optional `glow` override,
and a `watermarks` array.

`ScreenShell` deliberately supplies neither a position nor a height — the caller's
`className` does, because the three roots differ (`relative h-full w-full` on
eight screens, `absolute inset-0 z-40` on the waiting room, `fixed inset-0 z-50`
on game over). The source comment records why: a hardcoded `relative` would be
resolved against a passed-in `absolute` by stylesheet order, not attribute order,
and would silently win.

Two intended behaviour changes ride along: the watermarks and glow now hold still
instead of scrolling with the content, and `GameOverV2`'s confetti moves into the
backdrop so it rains down the screen rather than sliding away with the scoreboard.

`HomeScreenV2` had independently arrived at the same split (its bottom nav must be
a flow row *below* the scroller) and is deliberately not converted;
`RankPromotionSplash` and `RoundCelebration` already have non-scrolling roots.

## Complexity & Risk

**Low-to-medium.** 11 files, +227/-105, two commits, entirely presentational
client JSX/CSS. No state, no concurrency, no server, no protocol or schema
surface. Reverting is a clean `git revert` of two commits.

The risk that exists is concentrated in two places:

1. **Blast radius of the shared file.** `ScreenShell.jsx` is 79 lines but ten
   screens now depend on its exact box structure. A future edit that moves
   `{backdrop}` inside the scrolling div reintroduces the bug on all ten at once.
   Nothing automated would catch that.
2. **The failure mode is silent and visual.** The root's height/position contract
   is carried in a `className` string with no guardrail: a future caller that
   forgets the height class gets an auto-height root whose `h-full` scroller has
   nothing to fill. No error, no lint failure, no test — just a broken screen that
   only a human looking at it would notice.

Mitigating: I independently verified the PR's own verification claims —
`npm run lint` 0 errors / 12 pre-existing warnings all in untouched files,
`npm test` 86/86, `npm run build` clean. I also confirmed the invariant now holds
across the whole client: `grep` for `surface.base` shows it is on a
non-scrolling root in all twelve places it appears, and `overflow-y-auto` inside
`components/tableV2/*.jsx` appears only in `ScreenShell.jsx` and the documented
exception `HomeScreenV2.jsx`.

The correctness review found **no** behavioural regression across all ten screens
— backdrop prop values are byte-identical to the removed inline markup, containing
blocks and stacking order are preserved, and `position: fixed` descendants
(`StatsV2`'s `ArchetypeSheet`) still escape the new `overflow-hidden` because
neither new box applies `transform`/`filter`/`contain`/`will-change`.

## Findings

### Critical

**C1. `CLAUDE.md` does not document `ScreenShell`.**
`CLAUDE.md` → `#### The v2 UI (components/tableV2/)` documents every module of
this significance (`fanGeometry.js`, `layout.js`, `RoundLogRows.jsx`,
`suitShapes.jsx`, `SuitWatermark.jsx`, `HomeScreenV2.jsx`, `useHandGeometry.js`),
explaining the *why* and the failure mode rather than the what. `ScreenShell` is a
new shared module that ten screens depend on and that encodes a repo-wide
structural invariant — and it is absent. This repo's stated convention is that
hard-won lessons live in the repo, not in anyone's head. Add a bullet after the
`SuitWatermark.jsx` entry (which is also where the dependency points, since
`ScreenShell` imports it), covering: the two-box split, why a backdrop on a
scroller tiles and stops, why `overflow-hidden` on the root replaces per-screen
`overflow-x-hidden`, the list of ten converted screens, and why `HomeScreenV2` is
deliberately not one of them.

**C2. `docs/IOS-PWA-LAYOUT.md` § "What the home screen does now" is now
misleading.** That section presents the non-scrolling-root-plus-inner-scroller
split as a HomeScreenV2 idiosyncrasy, and its closing paragraph frames the
"decorative layers are now pinned to the viewport frame and no longer scroll with
the content" consequence as local to that one screen. Eleven screens now share
that shape. `CLAUDE.md` calls this doc "required reading before moving anything to
a screen edge", so a future reader is actively pointed at a stale description and
could reasonably re-derive a worse `ScreenShell`. Add a paragraph after the
existing one noting the split was generalised into `ScreenShell`/`ScreenBackdrop`,
listing the ten screens, and stating that HomeScreenV2 still hand-rolls it because
its bottom nav needs to be a flow row below the scroller — a shape `ScreenShell`
does not provide.

**C3. Nothing durable encodes the invariant this PR exists to establish.**
The PR's own framing is an invariant — *no element that carries a backdrop may
also be the element that scrolls* — and it was verified with a one-off automated
browser sweep over `/lobby /stats /leaderboard /activity /avatar /training /` that
was run once and discarded. There is a near-drop-in way to make that durable that
matches an existing repo pattern: `client/test/safeAreaHelpers.test.js` already
does a `readdirSync`/`readFileSync` scan over source under `node --test`, with no
DOM. Add `client/test/screenShellInvariant.test.js` that walks
`client/src/components/tableV2/*.jsx`, excludes `ScreenShell.jsx` (the owner) and
`HomeScreenV2.jsx` (the documented exception), and asserts none of the remainder
contain `overflow-y-auto`. **I verified this test passes today**, and it fails the
moment a new screen rolls its own scroller. Cost: one small file, no new
dependencies, no new infrastructure.

Caveat worth recording alongside it: `.github/workflows/test.yml` has only a
`server` job — there is no client test job at all, so even this test would guard
local `npm test` and review, not CI. That gap is pre-existing and out of scope
here, but it means C3's value is smaller than it looks until a client job exists.

### Suggestions

**S1. Several second watermarks are now permanently invisible on short phones.**
Because the watermarks moved out of the scroll, a watermark positioned below the
fold can no longer be reached by scrolling. The lower watermark's `top` per
screen: `ProfileV2` **620**, `GameReviewV2` / `StatsV2` / `TrainingV2` **580**,
`ActivityFeedV2` / `AvatarPickerV2` 560, `LeaderboardV2` 540, `LoginV2` 520,
`WaitingRoomV2` 460. On a ~667px-tall iPhone SE/8-class viewport, `ProfileV2`'s
leaves 47px of a 165px shape at 0.03 opacity — effectively dead markup. The same
tradeoff was already accepted for `HomeScreenV2` (`top: 520`, recorded in
`docs/IOS-PWA-LAYOUT.md`), but this PR pushes several screens noticeably further
down. Either pull the lower offsets under ~480 so they land on all supported
viewports, or accept and document the loss the way HomeScreenV2's is documented.
Note `useIsShortViewport()` already treats 760px height as the short tier, so the
repo's own definition of "short" is well above 620.

**S2. `ScreenBackdrop` should derive `tint` and `soft` from `useTableTheme()`
itself.** All nine backdrop-bearing screens thread `tint={surface.tint}
soft={soft}` through by hand, from the same hook call the screen already made, and
both are currently single app-wide constants. Defaulting them inside
`ScreenBackdrop` (keeping the props as overrides, since `GameOverV2` deliberately
omits the tint) removes nine identical lines and one whole category of "did I
forget to pass it" bug.

**S3. Extract the repeated watermark geometry.** Across the nine screens the only
things that vary are the two suits and the two `top` values. `size: 150`/`165`,
`rotate: -14`/`12`, `opacity: 0.03` on the second entry, `left: -46` and
`right: -52` are byte-identical everywhere. A helper —
`pairedWatermarks('H', 'S', [210, 560])` — would collapse each 7-line block to one
line and make the varying part the only visible part. It would also make S1 a
single-file change rather than a nine-file one.

**S4. Give `ScreenShell` named variants instead of a raw `className` contract.**
Eight of ten callers pass the byte-identical string `relative h-full w-full
font-sans`; only `GameOverV2` (`fixed inset-0 z-50`) and `WaitingRoomV2`
(`absolute inset-0 z-40`) differ. A `variant="fill" | "overlay" | "takeover"` prop
that bakes in the correct position+height would eliminate the silent-collapse
footgun for the common case while keeping the two special roots explicit.
`font-sans` is constant across all ten and could simply live inside the shell. The
existing comment correctly explains why a *hardcoded* `relative` is wrong; named
variants are the version of that idea that does not have the cascade problem.

**S5. `HomeScreenV2` should use `ScreenBackdrop` even though it can't use
`ScreenShell`.** Leaving it off the scroll wrapper is right — its bottom nav
genuinely must be a flow row after the scroller, and `docs/IOS-PWA-LAYOUT.md`
records real on-device breakage from getting that wrong. But `ScreenBackdrop` is a
plain fragment with no dependency on the wrapper, and `HomeScreenV2` lines 178-184
hand-write the same tint + glow + two watermarks with its own glow numbers. Using
`ScreenBackdrop` there leaves exactly one place that knows what the felt backdrop
looks like. (Prerequisite for a fully general version: S7.)

**S6. Add `ScreenShell` / `ScreenBackdrop` to the `components/tableV2/index.js`
barrel.** `SuitWatermark` and `MaxBotsChip` — the closest analogues — are both
exported there. Nine files import `ScreenShell` directly. Low stakes; the barrel
was already inconsistent (`AuthShell` is also omitted), but a nine-consumer shared
primitive is on the wrong side of that inconsistency.

**S7. `ScreenBackdrop`'s `glow` is unconditional while `tint` is guarded.**
`{tint && <div … />}` but the glow always renders. No current caller needs to omit
it, so nothing is broken — but the asymmetry is what blocks `RankPromotionSplash`
(which has its own rank-coloured halo/rays) from reusing the tint+watermark half.
Accepting `glow={false}` mirrors `tint`'s pattern for free.

**S8. `ScreenShell.jsx`'s cross-reference overclaims what the doc says.** The
header comment says "Deliberately not solved with `position: fixed` or
`background-attachment: fixed`. Read docs/IOS-PWA-LAYOUT.md before reaching for
either — it records what viewport-anchored boxes actually measured on device."
`background-attachment` appears nowhere in `docs/`. That doc's one on-device
measurement is about a *bottom-anchored* `position: fixed` tab bar losing 62pt.
A reader who follows the instruction finds no support for the claim. Either soften
the comment to say the `background-attachment` rejection is inference from the same
root cause rather than a separate measurement, or add a line to the doc saying so
— the doc's whole discipline is distinguishing measured from inferred.

Related, milder: the comment's blanket "deliberately not `position: fixed`" reads
as contradicting the doc's explicit § "What this rule does NOT say", and
`ScreenShell` is itself rendered with `fixed inset-0` by `GameOverV2`. The claim is
about the *backdrop layer*, not the root; saying so would stop the two comments
drifting.

**S9. The `LeaderboardV2` note in `docs/IOS-PWA-LAYOUT.md` now cites the wrong
file.** It says the sticky "me" row is "`position: sticky` inside its own scroller
(`LeaderboardV2.jsx`)". Still functionally true — sticky resolves against the
nearest scrolling ancestor either way — but the scroller is now
`ScreenShell.jsx`'s inner div, not anything written in `LeaderboardV2.jsx`.
Anyone chasing that citation to debug future sticky behaviour lands in the wrong
file.

**S10. The PR description's "the waiting room was the one that forgot" is not
quite right — `GameOverV2` forgot too.** On `origin/main`, `GameOverV2`'s root is
`fixed inset-0 z-50 overflow-y-auto font-sans` with no `overflow-x-hidden`, and it
draws a 560px-wide centred glow. On a 390px viewport that bleeds ~85px past each
edge, i.e. the same horizontal-scroll bug. The PR therefore fixes *two*
horizontal-scroll bugs, not one, and the "by-hand rule eventually gets it wrong"
argument is stronger than stated — it got it wrong twice out of ten. Worth
correcting in the description, since that argument is the PR's main justification
for the abstraction.

**S11. `AvatarPickerV2`'s confirm bar is the exact bug `LeaderboardV2`'s comment
warns about, and the new shell makes it a one-line fix.** The bar
(`AvatarPickerV2.jsx:107`, `absolute inset-x-0 z-20` / `bottom: 26`) is a child of
the scroller, so it is placed against the *scrolled* padding box: it sits at the
bottom edge only at `scrollTop 0` and rides up into the grid from there — verbatim
the failure `LeaderboardV2.jsx:263-269` documents and chose `sticky` to avoid. The
PR is right that it is unchanged (verified: same containing block before and
after), so this is pre-existing, not a regression. But `ScreenShell` now provides
exactly the box that fixes it: moving the bar out of `children` and into a sibling
of the scroller (or a third `footer` slot) pins it to the screen. Worth doing while
the file is open, or filing.

**S12. `GameOverV2`'s confetti has no reduced-motion guard; `RoundCelebration`'s
does.** The two confetti blocks are otherwise near-identical (same `top: -24`,
`9x14`, `borderRadius: 2`, same `cddConfetti ${dur} ${delay} linear infinite`);
`RoundCelebration` gates on `!rm`, `GameOverV2` does not. Pre-existing and outside
the diff's intent, but the PR moved this exact block, and reduced motion is a
first-class preference in this app (`useTableTheme`'s `rm`, `cddAlertRing` gated on
it, etc.). Worth a follow-up that both fixes the guard and extracts a shared
`<Confetti />`.

### Nits

**N1.** `ScreenBackdrop` keys watermarks by array index. The arrays are static
literals per screen, so this is fine as written — noting only so it stays that way
if a screen ever builds the list dynamically.

**N2.** `StatsV2`'s `ArchetypeSheet` now sits inside two nested `relative z-10`
stacking contexts (the shell's scroller, then the screen's content div) instead of
one. No visible effect today — nothing competes for z-order at that level — but
worth remembering if something ever needs to composite between the backdrop and
that sheet.

**N3.** `font-sans` appears in all ten callers' `className`. It is invariant and
belongs inside `ScreenShell` (folds naturally into S4).

**N4.** No plan document exists under `.agents/plans/` for this refactor; its only
trace is the two commits. Process observation rather than a code finding.

### Questions

**Q1.** Was the "no backdrop-carrying box scrolls on any route" sweep script kept
anywhere, or discarded? If it exists, it may be cheaper to adapt than to write C3
from scratch.

**Q2.** Is the watermark visibility loss in S1 an accepted tradeoff (as it is for
HomeScreenV2), or an unnoticed side effect? The answer changes whether S1 is a
code change or a doc change.

**Q3.** Is a `footer` slot on `ScreenShell` (which would let `HomeScreenV2` and the
avatar picker's confirm bar both use it — see S5, S11) worth doing, or is one
shell per shape the right call? The PR's exemption reasoning is sound; the
question is whether it should stay permanent.

**Q4.** The description's "One gap" notes Stats/Leaderboard/Activity were verified
structurally rather than visually on a data-rich account, because guests 404 on the
stats endpoints. Is anyone able to eyeball those three on a real account before
merge? They are the three longest-scrolling screens, i.e. the ones the seam was
most visible on.

## Correctness

No CRITICAL, HIGH or MEDIUM correctness issues. Verified across all ten screens:

- Every root's `className` still supplies a position and a definite height, so the
  inner `h-full` scroller resolves exactly as the old root did.
- `ScreenBackdrop` prop values are byte-identical to the removed inline markup on
  all ten screens — glow width/height/top and watermark suit/size/rotate/opacity/
  style — including `LoginV2`'s `{560, 380, top: '-120px'}` and `GameOverV2`'s
  `{560, 380}` with the default `top`.
- `GameOverV2` correctly omits `tint`; `ScreenBackdrop`'s `{tint && …}` guard
  handles `undefined`, and the glow still renders.
- `AvatarPickerV2`'s absolute confirm bar and `LeaderboardV2`'s sticky row keep the
  same containing block / scroll anchor: their nearest positioned scrolling
  ancestor moved from the old root to the new inner scroller, which is sized and
  behaves identically.
- `StatsV2`'s `ArchetypeSheet` (`position: fixed`, z 90/95) is unaffected by the
  root's new `overflow-hidden` — neither box applies `transform`, `filter`,
  `will-change` or `contain`, so no containing block is established for fixed
  descendants and the modal still escapes to the viewport.
- `GameOverV2`'s confetti keeps its paint order: the scroller's `z-index: 10`
  composites above the confetti's `z-index: 5`, matching the pre-PR relationship
  between the content div (z-10) and the confetti (z-5).
- No converted screen uses `overflow-x-auto` or a wide table that the root's
  `overflow-hidden` would now clip.
- `WaitingRoomV2`'s `absolute inset-0` resolves against `.game-screen-safe`
  (`GameRoom.jsx:982`, `position: fixed` with all four insets), confirmed as its
  positioned ancestor with no intervening wrapper.

Layout-specific checks that also came back clean:

- **Safe areas.** `env(safe-area-inset-*)` is viewport-relative, not
  nesting-dependent; the `pb-safe-*`/`pt-safe-18` classes sit on the same content
  div, still a normal in-flow descendant, and no root changed position type.
  `docs/IOS-PWA-LAYOUT.md`'s warning is specifically about bottom-only `fixed`
  elements — none introduced.
- **Scroll semantics.** `html, body { overflow: hidden }` (`index.css:19-24`) means
  `#root` was already the practical scroller, not the document; status-bar
  tap-to-top targeted `document.scrollingElement` and already did nothing. The
  change adds one non-scrolling `overflow: hidden` wrapper, so no double-bounce and
  no new scroll container. `overscroll-behavior: none` is on `html`/`body`,
  unchanged.
- **Confetti travel.** `cddConfetti` runs `translateY(-30px) → translateY(900px)`
  (`index.css:176-179`). `GameOverV2`'s containing block was `fixed inset-0` both
  before and after, so the distance is unaffected; the move out of the scroller is
  a genuine fix, since absolutely-positioned descendants of a scroller do move with
  its scroll offset.
- **Desktop.** `GameOverV2`'s `md:justify-center` on a `min-h-full` column resolves
  against the same definite-height box as before.

## Maintainability

The abstraction is well-judged: it is extracted from ten real call sites rather
than invented up front, the split it encodes is the actual fix rather than
decoration, and the header comment explains the failure mode rather than
restating the code — all in keeping with `layout.js` and `fanGeometry.js`.
The decision *not* to hardcode `relative` (and the recorded reason) is exactly
right and would have been an easy trap to fall into.

What is left on the table is duplication the extraction could have absorbed but
didn't: `tint`/`soft` threaded by hand nine times (S2), watermark geometry repeated
nine times with two varying fields (S3), and eight identical `className` strings
guarding a contract with no guardrail (S4). `HomeScreenV2` still hand-writes the
same backdrop trio (S5), so there are now two places that know what the felt looks
like rather than one. None of these block merge; together they are the difference
between an abstraction that removes the duplication and one that relocates it.

Checked and correctly excluded from scope: `RoundCelebration` uses no
`SuitWatermark` at all; `RankPromotionSplash` uses a rank-coloured halo the fixed
`soft` ellipse cannot express (S7 is the prerequisite for reusing it);
`TableBackground` is the live in-game felt with percentage ellipses, three
watermarks and no scrolling context, and is not a "screen" in this sense.
