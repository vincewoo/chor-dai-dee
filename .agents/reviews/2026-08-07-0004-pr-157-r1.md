## Summary

Accumulates each round's deal-strength score per seat for the whole game and
surfaces it on the game-over screen: a `Deal strength: 1st (61st percentile)`
line on every standings row, plus a collapsible rounds × players round-review
grid (deal percentile, colour-banded, with points/cards-left per round).

## How It Works

**Server.** `DealStrength.rankTable()` has always scored all four dealt hands at
the top of every round (`Room.recordDealStrength()`, `RoomManager.js:1061`), but
it wrote only into `this.roundDealStrength`, which is wiped on the next deal. The
PR adds a second, longer-lived sink:

1. `recordDealStrength()` now also pushes
   `{ round, points: null, cardsLeft: null, won: false, percentile, tierLabel, rank }`
   into `this.roundHistoryByName[player.name]` (`RoomManager.js:1089`). Keyed by
   **name**, not socket id — the stated reason being that `roundPlayStats` is
   id-keyed and has to be hand-migrated in three places on reconnect and bot
   swap, whereas a name "survives all of that untouched."
2. `updateScores()` (`RoomManager.js:1116-1126`) closes each round's entry out at
   round end, matching on `roundHistoryByName[s.name]` and the round number, and
   filling in `points`, `cardsLeft` and `won`.
3. The accumulator resets inside `startGame()`'s `roundNumber === 0` branch
   (`RoomManager.js:826`), alongside `roundsWonByName` and `gameStartedAt` — the
   room's single "a new game is starting" signal, reached by both `startRematch()`
   and the lobby restart.
4. `Room.describeRoundReview()` (`RoomManager.js:1017`) folds that into
   `{ [name]: { avgPercentile, dealRank, totalPoints, roundsWon, rounds[] } }`.
   `avgPercentile` is the rounded mean of the seat's per-round percentiles;
   `dealRank` is a **game-level** ranking that keeps an unrounded `mean`, sorts
   `Object.keys(out)` on it descending, assigns 1..N with ties meant to share the
   better rank, then deletes the temporary `mean`.
5. It is attached as `roundReview` to exactly two payloads: `game_over`
   (`index.js:1184`) and `dragon_win` (`index.js:870`). Both are built after
   `room.gameState = 'finished'`. It is deliberately absent from `getGameState()`
   and `round_over`, because `rank` compares all four dealt hands and is a live
   read on opponents' holdings (the SECURITY note on `DealStrength.rankTable`).

**Client.** `GameRoom` already stores the whole `game_over` / `dragon_win` payload
in `gameOver` state and passes it to `GameOverV2`. `GameOverV2.jsx:33-34` pulls
`avgPercentile` and `dealRank` off `gameOver.roundReview[s.name]` — a **name-keyed
lookup against the standings row's name** — and the subtitle under each row now
renders `Deal strength: 1st (61st percentile)`, *replacing* the previous
`Winner` / `Nth place` text (which survives only as a fallback when `dealRank` is
null). `RoundReviewPanel.jsx` renders the drill-in: a `<table>` whose columns are
the union of every round anyone was dealt into, whose cells print
`Math.round(percentile)`, and whose cell colour is banded on the same number
(`>= 67` accent, `< 34` salmon, else muted). Rank now appears only in the cell's
`title` tooltip.

## Complexity & Risk

**High**, and higher than the diffstat suggests. Only 8 files change and the
server side is a pure read — nothing about gameplay, scoring, ratings or
persistence changes, so a revert is trivial and carries no data consequences.
The leak boundary, the scariest part on paper, is in good shape (see Security).

The risk is concentrated in two places:

1. **The accumulator is keyed on a mutable display name, and the codebase renames
   seats mid-game.** Both `replaceWithBot()` (`Bot (Alice)`) and `replaceBot()`
   (a mid-game joiner taking a bot's seat) change `player.name` on a live seat,
   and neither touches `roundHistoryByName`. That produces more keys than there
   are seats, which the game-level `dealRank` then ranks over — with directly
   visible wrong output. Both paths are ordinary advertised product behaviour
   (leaving a game in progress; joining one from the home screen's Live list),
   not exotic edge cases.
2. **Five commits in, the prose has not kept up with the code.** Three separate
   comments now assert things the code does not do, one of which (the tie
   convention) is a real logic bug hiding behind a confident docblock and a test
   named after the behaviour it fails to check.

Separately, keying a plain object on a username turns out to be exploitable
(C6): the `||= []` shape crashes on `Object.prototype` names that
`validateUsername` currently permits.

Riskiest specific lines: `RoomManager.js:1042-1047` (the ranking loop — both the
`Object.keys` domain and the `delete` ordering) and `RoomManager.js:1089` /
`:1118` (name as the accumulator key, on both write and close-out).

## Findings

### Critical

---

**C1 — The tie-sharing branch can never fire: `mean` is deleted before the next
iteration reads it.**
`server/game/RoomManager.js:1042-1047`

```js
const order = Object.keys(out).sort((a, b) => out[b].mean - out[a].mean);
order.forEach((name, i) => {
    const tied = i > 0 && out[name].mean === out[order[i - 1]].mean;
    out[name].dealRank = tied ? out[order[i - 1]].dealRank : i + 1;
    delete out[name].mean;          // <- runs before iteration i+1 reads it
});
```

At iteration `i`, `out[order[i-1]].mean` was deleted at the end of iteration
`i-1`. The comparison is therefore always `<number> === undefined` → always
`false`. Not "sometimes wrong" — **no tie is ever detected, for any pair, ever.**
Verified by replicating the loop with forced ties:

```
input:    A=90, B=90, C=50, D=50
expected: A=1, B=1, C=3, D=3     (ties share the better rank)
actual:   A=1, B=2, C=3, D=4
```

The docblock three lines above says this exists "so the tie convention matches
`DealStrength.rankTable`: ties share the better rank, so two equal games are not
arbitrarily declared better and worse than each other." That is exactly what the
code does instead.

This is not hypothetical. Simulating real 4-player games, the probability that at
least two seats end with an exactly equal mean percentile:

| rounds | P(a tie exists) |
|---|---|
| 1 | **32.9%** |
| 4 | 1.4% |
| 6 | 1.1% |
| 8 | 0.9% |
| 12 | 0.8% |

~1% of ordinary games, and **a third of one-round games — which is precisely the
dragon-win case**, the one place a tie is most likely and most conspicuous.

*Fix:* assign every `dealRank` in one pass reading `.mean` throughout, then strip
`.mean` in a second pass — or rank from a local array and never put the scratch
field on the returned object at all. The latter also removes the need for the
test that exists solely to assert the scratch field did not escape.

*Why the test missed it:* `dealStrength.test.js`'s `'deal strength is ranked
across the game, ties sharing the better rank'` never constructs a tie. Its three
assertions all pass with the bug present — `ranks[0] === 1` holds, monotonicity
by `avgPercentile` holds (ranks are still assigned in sorted order), and
`!('mean' in e)` holds because each entry's own `mean` *is* deleted in its own
iteration. The test is named after the one behaviour it does not exercise.

**C2 — `dealRank` ranks over orphaned name keys, so a 4-player game can show
"Deal strength: 5th" and no 1st place at all.**
`server/game/RoomManager.js:1042`, rendered at
`client/src/components/tableV2/GameOverV2.jsx:33-34, 160-161`

`Object.keys(out)` is every name that was ever dealt a hand this game, not the
four names currently seated. Any mid-game seat rename adds a key, so `dealRank`
runs 1..N for N > 4.

Reproduced against the real `Room` class. **A single mid-game join is enough** —
no rage quit required:

```
seats:  [ 'Alice', 'Charlie', 'Bot 3', 'Bot 4' ]
keys:   5
  Alice        dealRank=4  avg=32  rounds=1,2,3
  Bot 2        dealRank=1  avg=72  rounds=1,2      <- departed, not on screen
  Bot 3        dealRank=2  avg=63  rounds=1,2,3
  Bot 4        dealRank=3  avg=63  rounds=1,2,3
  Charlie      dealRank=5  avg=23  rounds=3
```

The four standings rows render **2nd, 3rd, 4th and 5th** — nobody is 1st, and
"Deal strength: 5th" is impossible at a four-seat table. With a rage quit
(`replaceWithBot`) *and* a join I got six keys and a literal `Deal strength: 6th`.
Because the subtitle now *replaces* the placement text (see S6), that nonsense
ordinal can land on the actual game winner's row where the word "Winner" used to
be.

Compounding it, `dealRank` compares means computed over **different numbers of
rounds**, with no minimum-round gate. In the run above `Charlie`'s single round is
ranked against three-round means; in another run a one-round seat took
`dealRank=1` on an `avg=92` that is pure small-sample variance. This is the same
failure mode `MIN_ROUNDS_FOR_EDGE = 50` exists to prevent for career Edge
(`DealStrength.js:56-61`), and the PR's own description argues at length that a
6–10 round sample is too small for a verdict — then ranks 1-round samples against
12-round ones without comment. Quantified over 20,000 Monte-Carlo trials with
real `Room`/`DealStrength` code, three 8-round veterans against one 1-round
joiner and **no orphaned keys involved at all**: the joiner takes `dealRank` 1
— "best deal luck of the whole game" — **39.5% of the time**, against the 25%
a fair comparison would give. Top-2 placement came out at 48.9%, near the 50%
baseline, so the distortion is concentrated exactly at the extreme the UI states
most confidently. Simulation also puts the p5–p95 spread of a 3–4-round mean at
48–56 points against 20–34 points at 12–14 rounds.

*Fix:* rank over the currently seated names only, resolving `p.replacedHuman.name`
the way `describeParticipants()` does (`RoomManager.js:2208`), and — per C3 —
over merged per-seat histories. `dealRank` must be bounded by the seat count.
Separately consider gating or annotating entries below some minimum round count.

**C3 — A seat's history splits across two keys when the seat is renamed mid-game,
so real rounds are dropped from the average and rendered as "never dealt".**
`server/game/RoomManager.js:1089` (write) vs `RoomManager.js:495-497` (rename);
consumed at `GameOverV2.jsx:33` and `RoundReviewPanel.jsx:119`

`recordDealStrength()` keys on the **live** `player.name` at deal time.
`replaceWithBot()` renames the seat to `` `Bot (${oldPlayer.name})` `` and is
called on every ordinary mid-game leave (`server/index.js:2115`, and again at
`:454` when a player leaves by joining another room). Reproduced:

```
players: [ 'Bot (Alice)', 'Bob', 'Bot 3', 'Bot 4' ]
  Alice        avg 16  rounds 1,2      <- orphaned: no standings row is named "Alice"
  Bot (Alice)  avg 12  rounds 3,4
  Bob          avg 67  rounds 1,2,3,4
```

The standings row for that seat is named `Bot (Alice)` (`Scoring.js` copies
`p.name` straight off the live `room.players`), so:

- its `avgPercentile` averages **only the post-swap rounds**, silently excluding
  the human's real rounds 1–2;
- the panel renders `–` for rounds 1 and 2 on that row — and the panel's own
  comment says `–` means "a seat that was never dealt this round has no deal",
  which is false here: the seat *was* dealt, twice;
- those round numbers are still pulled into the column headers by the
  `Object.values(roundReview)` union (`RoundReviewPanel.jsx:42-48`), so the blanks
  are conspicuously present rather than absent.

This is precisely the failure mode the codebase already solved once. Compare
`describeParticipants()` (`RoomManager.js:2208`), whose docblock explains the same
hazard for `roundsWonByName` and resolves it with
`const human = p.isBot ? p.replacedHuman : null;`. `describeRoundReview()` has no
equivalent, and `replaceWithBot()` — which migrates `cumulativeScores`,
`playerLastPlayed`, `passedPlayers`, `roundPlayStats` and `tier3DecisionTracking`
between ids — was not extended to move `roundHistoryByName` between names.

The stated rationale for name-keying ("a name survives all of that untouched",
`RoomManager.js:820-824`) is the load-bearing claim here, and it is not correct:
a socket id survives a rename, and a name survives a reconnect. The two failure
modes are different, not nested. See Question 1.

**C3b — `e81653a` extends C3 into the new scoreboard: a renamed seat loses a
whole round's score, and `totalPoints` silently disagrees with the standings.**
`server/game/RoomManager.js:1116-1126`

`updateScores()` closes out each round's entry by looking up
`this.roundHistoryByName[s.name]`. If the seat was renamed *during* the round, the
entry was pushed under the old name at deal time and the lookup misses, so
`if (!entry) return;` leaves that round permanently at
`points: null, cardsLeft: null, won: false`. Reproduced:

```
Alice        totalPoints=0   roundsWon=0   rounds=[{rd:1, pts:null, won:false}]
Bob          totalPoints=6   roundsWon=1   rounds=[{rd:1, pts:6,    won:true }]
Bot 3        totalPoints=9   roundsWon=0
Bot 4        totalPoints=12  roundsWon=0
cumulativeScores: { ..., bot_..._replacement: 3 }     <- the seat really scored 3
```

The seat scored 3 points; the review reports 0 for it, and reports nothing at all
under the name actually shown in the standings (`Bot (Alice)` is not a key —
it was never *dealt* under that name). `describeRoundReview`'s docblock claims
`totalPoints` is "totalled from the scored rounds only, so it agrees with the
standings even when a dealt round was never scored." Here a round that *was*
scored is recorded as unscored, and the two numbers disagree on screen.

The `if (!entry) return;` guard is doing exactly what its own comment promises
("a score arriving for a round that was never dealt … cannot corrupt another
round's row") — the problem is upstream: the key is not stable.

*Fix:* the same one as C3. Fixing the keying fixes this for free.

**C4 — Neither C2 nor C3 has a test, and both are reachable from ordinary product
paths.**
`server/test/dealStrength.test.js`

Seven tests were added and they cover the accumulator's lifetime (survives a
round, resets on rematch) and the leak boundary well. But nothing in the suite
ever calls `replaceWithBot()` or `replaceBot()` — the two functions that break the
keying scheme the whole design rests on. The suite's own framing makes this
conspicuous: `describeRoundReview`'s docblock *names* mid-game joiners as a
handled case, and the accumulator's comment *names* bot swaps as the reason for
the design, yet neither is exercised.

Three more gaps worth closing at the same time:

- **The tie branch never ties** (C1) — the single highest-value missing test.
- **The divisor is unpinned.** The mean divides by `rounds.length`, and every
  existing test has `rounds.length === roundNumber` for every entry. A refactor to
  `this.roundNumber` (in scope, right there) would pass the whole suite.
- **The leak test has already rotted once.** `dealStrength.test.js:227` still
  asserts `!('dealHistoryByName' in room.getGameState())` — a field `e81653a`
  renamed to `roundHistoryByName`. That assertion is now vacuously true and pins
  nothing. Line 225 was updated to `roundReview`, so the rot is partial, which is
  the more dangerous kind. This is a live demonstration of the weakness noted
  under Security: name-based leak assertions do not survive renames.

*Suggested tests:* (a) four seats, two rounds, `replaceWithBot` one of them, two
more rounds — assert the seat's entry covers all four rounds, that
`max(dealRank) <= room.players.length`, and that `totalPoints` equals the seat's
cumulative score; (b) the same with `replaceBot`; (c) a constructed tie;
(d) a hand-seeded two-round mean against a computed value including a `.5` case;
(e) replace the string-matching leak test with a key-set snapshot of
`getGameState()`.

**C5 — The `dragon_win` comment's two claims are both false, and the dragon screen
is incoherent as a result.**
`server/index.js:866-870`

```js
// A dragon ends the game on round 1, so this is a single round --
// and the dragon holder is rank 1 by definition, since 13 distinct
// ranks is the strongest deal there is.
roundReview: room.describeRoundReview()
```

Both halves are wrong, and I measured rather than assumed:

1. **A dragon does not imply round 1.** The dragon check lives inside
   `startRound()` (`RoomManager.js:871-892`), which runs every round via
   `handleNextRound()`. A dragon dealt in round 5 ends the game with five rounds
   of accumulated history in the payload.
2. **The dragon holder is not rank 1 "by definition".** `rawDealStrength` prices
   *control* (2s, aces, kings) against *plays needed to shed*, and a dragon — one
   card of every rank, thirteen distinct rank groups — is mediocre on both:

   ```
   dragon (no 2♠)       raw = 2    tier "Strong"   percentile 69
   dragon (with 2♠)     raw = 3    tier "Strong"   percentile 76.5
   3×2s + 3×A + 3×K + … raw = 17
   ```

   Over 4,000 simulated deals where one seat holds a dragon and the other 39 cards
   are dealt at random, the dragon holder is **rank 1 only 17.3%** of the time
   (distribution 1:691, 2:1921, 3:1200, 4:188).

The runtime consequence is user-visible: the dragon-win screen puts a giant
"🐉 Dragon win!" hero above a standings row that, five times out of six, reads
`Deal strength: 2nd (69th percentile)` or worse for the player who just won the
entire game outright by holding the rarest hand there is. And per C1, a one-round
game is the case where ties are most likely (32.9%) and tie-sharing is broken.

*Fix:* correct both clauses of the comment. Separately decide what the dragon
screen should say — suppressing the deal line on a dragon win, or special-casing
the dragon as the strongest deal, are both defensible; the metric quietly
contradicting the game's own headline is not.

**C6 — A player registered as `constructor`, `toString`, `__proto__`,
`valueOf` or `hasOwnProperty` crashes `startGame()` and bricks the table.**
`server/game/RoomManager.js:1089`

```js
(this.roundHistoryByName[player.name] ||= []).push({ ... });
```

`roundHistoryByName` is a plain `{}`, so for any `Object.prototype` key the
bracket read returns an inherited, **truthy** value — `||=` therefore never
assigns, and `.push` is called on `Object`/`Function.prototype.toString`/the
prototype itself. Every one of those names passes `server/username.js`'s
`validateUsername` (3–20 chars, `^[a-zA-Z0-9_]+$`, only `guest_` is a reserved
prefix), so they are registrable today:

```
validateUsername('__proto__')     -> { ok: true }
validateUsername('constructor')   -> { ok: true }
validateUsername('toString')      -> { ok: true }
validateUsername('hasOwnProperty')-> { ok: true }
```

Executed against a worktree pinned to the pushed `e81653a`:

```
"constructor" -> THREW: TypeError: this.roundHistoryByName[player.name].push is not a function
"__proto__"   -> THREW: TypeError: ...
"toString"    -> THREW: TypeError: ...
"Alice"       -> OK
```

`recordDealStrength()` is called synchronously from `startRound()` ← `startGame()`
← the `start_game` socket handler, which has no `try/catch`. The throw aborts the
handler mid-flight: no `game_started` emitted, no hands dealt out, and the room
left half-started (`roundNumber` incremented, `gameState` mutated) with every
player at the table stuck. It reproduces on that account's every game, forever.
The process itself survives (`index.js` registers an `unhandledRejection`
handler that only logs), so this is a per-room denial of service rather than a
server outage.

Note this is a **new** exposure, not pre-existing: `roundsWonByName` uses the
same plain-object-keyed-by-username pattern, but its
`(x[name] || 0) + 1` degrades silently rather than throwing. The `||= []` +
`.push` shape is what turns it into a crash.

*Fix:* `Object.create(null)`, or a `Map`, for anything keyed on a
user-controlled string. The uncommitted seat-index rework removes the crash —
but `describeRoundReview()` still builds its output as `out[name] = {...}` on a
plain object, so a player named `__proto__` now silently disappears from the
review instead (verified: review keys come back as `['Bot 2','Bot 3','Bot 4']`
with the human absent, because assigning to `out['__proto__']` invokes the
prototype setter and creates no own property). Worth fixing in the same pass,
and worth considering whether `username.js` should reject `Object.prototype`
keys outright given how many places key on a username.

### Suggestions

**S1 — "Nth percentile" borrows an intuition that does not transfer to a
game-mean.** The mean of N per-round percentiles concentrates near 50 by CLT, so
the displayed number lives on a much narrower distribution than a single hand's
percentile does. Simulated against the repo's real `Deck` and `DealStrength`:

| rounds | p5 | p25 | p50 | p75 | p95 |
|---|---|---|---|---|---|
| 4 | 25.5 | 39.3 | 49.8 | 59.5 | 73.5 |
| 8 | 32.7 | 42.7 | 49.6 | 56.6 | 66.4 |
| 12 | ~35.8 | — | 49.8 | — | ~63.3 |
| 20 | 39.1 | 45.3 | 49.5 | 54.0 | 60.0 |

A displayed **64** is the ~92nd percentile of player-games at 8 rounds and ~96th
at 12–14 — near the top of the luck distribution — while "64th percentile" reads
as a mild B-minus. Commit `7f71f27` softened this considerably by promoting
`dealRank` to the headline and demoting the percentile to a parenthetical, which
is the right call. The remaining ask is either to drop the word "percentile" for
the game-level figure or to re-baseline it against the distribution of game means.

Worth recording that the design rationale **did** hold up under independent
check. The doc's claimed table reproduced almost exactly (mean tier index
p5/p50/p95 = 1.167/1.833/2.500 vs the claimed 1.17/1.83/2.50; mean percentile
35.79/49.75/63.33 vs 35.7/49.8/63.6; "Average" printed 77.8% vs the claimed
77.3%). And the number genuinely discriminates between seats: median across-seat
spread is 17–27 points at realistic lengths and under 5 points only ~1–2% of the
time, because control is near-constant across the four hands each round so the
seats are anti-correlated. Both are load-bearing claims and both check out.

**S2 — `dealRank` ranks on a different statistic from the one it claims to
match.** The per-round `rank` comes from `rankTable`, which ranks by **raw**
score. `dealRank` ranks by **mean percentile**, and `percentileFor` is a
saturating non-linear monotone map of raw — so averaging after the transform is
not the same statistic as averaging before it. Over 200k randomised round
sequences the two orderings disagreed in ~11.4% of trials. The comment's claim
that this is done server-side "so the tie convention matches
`DealStrength.rankTable`" is true only of the tie *rule* (which per C1 does not
work); the comparison basis is materially different. Not wrong in isolation —
percentile is the number already shown — but the docblock should say so rather
than imply equivalence.

**S3 — Seats with unequal round counts are shown with false comparability.**
Related to C2 but survives any fix to it: a mid-game joiner's `avgPercentile` and
a full-game player's are printed identically, at the same precision, on adjacent
rows, with nothing signalling that one is a 3-round estimate and the other a
12-round one. Consider suppressing the game-level figure below a minimum round
count, or annotating it with the count.

**S4 — Rank is now shipped but only reachable by hover.** Since `6b7aaf4` the
grid colours by absolute strength and `rank` survives only inside the cell's
`title` attribute (`RoundReviewPanel.jsx`). `title` does not fire on touch, and
this is the primary mobile game-over screen. The field with the entire SECURITY
docblock attached to it is now, in practice, invisible to most of the people it
was added for. Either surface it without hover (an `aria-label`, or a visible
glyph) or stop sending it.

**S5 — The grid's meaning is carried by colour alone, and two of its states are
nearly identical.** Three bands (accent `#ffc94d`, `MUTED` = 50%-opacity white,
`#ff8f70`) applied to 12px text. Two specific problems:

- The middle "average" band (`MUTED`, 50% white) and the "no deal" placeholder
  (`FAINT`, 38% white) are the same base colour 12 alpha points apart. Two
  semantically different states — "average deal" and "no data" — read the same at
  12px.
- Composited against the real rendered stack (the page's dark-green radial
  gradient under the panel's `rgba(0,0,0,.3)`), the three bands measure roughly

### Questions

1. **Is name-keying still the right call?** The stated reason was to avoid the
   three hand-migrations `roundPlayStats` needs. But `replaceWithBot` already
   performs five such migrations in a row, so adding a sixth is a one-line change
   in a function already doing exactly this. Was **seat-index** keying considered?
   The ML game log keys on seat index for what reads like the same reason
   ("socket ids change mid-game on reconnect and on bot/human swaps"), and a seat
   index survives a rename *and* a reconnect — which is what this feature actually
   needs. C2, C3 and C3b all collapse into nothing under seat-index keying.
2. **What should a dragon win show?** See C5. Suppress, special-case, or accept
   that the metric does not value a dragon?
3. **Should `dealRank` exist at all**, given S1 (the percentile it ranks on is a
   compressed statistic) and C2 (the seats ranked may have wildly different sample
   sizes)? A three-way "who got the cards" split — top / middle / bottom — would be
   robust to both in a way a strict 1-2-3-4 ordering is not.
4. **Is removing "Winner" / "Nth place" from the standings rows intended?** (S6)
5. **`start_game` has no `gameState` guard — does this PR make that visible?**
   `socket.on('start_game', …)` (`server/index.js`) does not check whether a game
   is already running, and neither `GameRoom.jsx` nor `Lobby.jsx` debounces the
   emit. A double-fire (double-tap before the UI transitions, or a duplicate emit
   on reconnect) calls `startGame()` twice: the second call skips the
   `roundNumber === 0` reset but still does `roundNumber++; startRound()`,
   dealing a second hand over the first. Pre-existing and out of scope, but this
   PR is the first thing that makes the discarded round *visible* — it stays in
   the accumulator and renders as a real column in the grid for a round nobody
   played. Flagged at moderate confidence (I did not rule out a de-dup layer I
   missed); worth a look because the fix is a one-line guard.
6. **Is the 5th commit (`e81653a`) meant to be in this PR?** It expands the scope
   from "deal luck" to a full round-by-round scoreboard, renames every public
   symbol the earlier commits introduced, and adds server-authoritative
   `points`/`cardsLeft`/`won` fields with no new tests. It is also the commit that
   introduced C3b and rotted the leak assertion (C4). Splitting it out would make
   both halves reviewable.

## Correctness

Confirmed: C1, C2, C3, C3b, C5. Also verified and found **safe**:

- **Reconnect.** `reconnectPlayer()` (`RoomManager.js:253-330`) mutates `id`,
  `socket` and `isDisconnected` but never `name`, so name-keying does survive a
  reconnect as claimed.
- **Plain disconnects do not swap the seat.** `replaceWithBot` has exactly two
  callers (`server/index.js:454`, `:2115`), both explicit leaves. A transient
  network drop leaves the player in place as `isDisconnected`, so C2/C3 are not
  triggered by ordinary connectivity blips.
- **Rematch and lobby restart.** Both `startRematch()` and `transitionToLobby()`
  set `roundNumber = 0` before the next `startGame()`, and no path reaches
  `startRound()` without that reset — `next_round` is gated on
  `gameState === 'round_over'` and never calls `startGame()`. The reset test is
  real.
- **Shared mutable state.** `describeRoundReview()` returns the live `rounds`
  arrays by reference into `room.lastGameResults`, but the only reset path
  replaces the container with a *new* object rather than mutating the arrays, so
  a replayed game-over payload cannot be corrupted. (Note `e81653a` now mutates
  those arrays post-hoc in `updateScores`, but only during a live game.)
- **`mean` does not escape to the client.** Every entry's own `mean` is deleted in
  its own iteration regardless of C1, so the payload is clean. The test asserting
  this is true but not diagnostic.
- **Username collisions with bot names.** `server/username.js` restricts
  registered names to `[a-zA-Z0-9_]` and reserves the `Guest_` prefix, so no
  human can register a name colliding with `Bot 2` (space) or `Bot (Alice)`
  (space, parentheses). *(That charset does not save it from C6.)*
- **Reconnect after a bot swap.** `replaceWithBot` deletes
  `playersByUsername[oldName]`, so `canReconnect()` returns false and the
  original human cannot resume that seat — they would have to rejoin via
  `replaceBot()`. Under the pushed name-keying that rejoin would silently reunite
  them with their orphaned key and splice two non-contiguous stints into one
  average with no gap indicator. Narrower than C3 and moot under seat-index
  keying; noted for completeness.
- **`ordinalSuffix`.** Correct across the whole reachable range, including the
  11/12/13 exception and 0 and 100. It renders `5th`/`6th` happily for C2's
  out-of-range `dealRank`, which is how that bug surfaces rather than throwing.
- **Colour band boundaries vs the printed number.** The cell colour uses the
  *unrounded* percentile while the cell prints the rounded one, so a value of
  33.5 or 66.5 would be coloured against what the legend says. I enumerated all 29
  reachable raw scores: the reachable percentiles are 0, 1, 4, 8.5, 14.5, 22.5,
  32, 42, 51.5, 60.5, 69, 76.5, 83, 88, 91.5, 94, 96, 97.5, 98, 98.5, 99 — none
  lands on a boundary half. **Zero contradictions today**, but safe by luck rather
  than by construction: threshold on the same rounded value that is displayed.

## Security

**The leak boundary holds.** Traced every path; no way for `roundReview` or
`roundHistoryByName` to reach a client before the game ends:

- `describeRoundReview()` has exactly two callers, both after
  `room.gameState = 'finished'` (`server/index.js:843` before `:870`; `:1162`
  before `:1184`).
- `getGameState()` is a hand-written whitelist and carries no deal fields.
- `round_over`'s payload is `{ roundWinner, scores, roundNumber }`;
  `room.roundDealStrength` is read only for the server-side DB write at
  `index.js:1127` and never placed on a socket payload. A player does **not**
  receive other players' deal strength mid-game.
- Every one of the ~8 replay paths (`reconnected`, "already in room",
  `replaceBot`, `spectate_room`, `get_room_state`) gates the game-over replay on
  `gameState === 'finished' && lastGameResults`, and both `startRematch()` and
  `transitionToLobby()` null `lastGameResults` before a new game can deal.
- No spread or serialization of the whole `Room` object anywhere, so the new
  instance field cannot ride along incidentally.
- No reference to the accumulator or the describe method in `gamelog.js`,
  `gamelogRecorder.js`, the tape codec, or any export path.

Residual note, informational: `game_over` and `dragon_win` are
`io.to(roomId).emit`, so spectators receive `roundReview` too, and spectating is
unauthenticated. Consistent with the feature's intent (a public game-over screen)
and it only fires once the game is finished, so it does not violate the mid-round
invariant — but a completed game's full four-seat deal breakdown is now visible to
anyone who was spectating, where previously it never left the server.

The real ask is C4's test point: the boundary is pinned by field *name*, and the
rename in `e81653a` already left half of that assertion vacuous.

## Statistics

All simulated against the repo's real `Deck.js` and `DealStrength.js`.

- **Doc's claimed table: verified.** Mean tier index p5/p50/p95 measured
  1.167/1.833/2.500 vs claimed 1.17/1.83/2.50; mean percentile 35.79/49.75/63.33
  vs 35.7/49.8/63.6; "Average" 77.8% vs claimed 77.3%. The design rationale is
  sound.
- **The number discriminates.** Across-seat spread of `avgPercentile` has a median
  of 17–27 points at realistic lengths and is under 5 points only 1–2% of the
  time — control sums to a near-constant across the four hands each round, so the
  seats are anti-correlated and the spread is amplified relative to four
  independent draws. The standings line earns its space.
- **But the label overstates modesty** (S1), and **the ranking basis is not the
  one the comment claims** (S2, ~11.4% disagreement with a mean-raw ranking).
- **Exact ties are common enough to matter** — 0.8–1.4% of normal games and 32.9%
  of one-round (dragon) games, which is what makes C1 a real bug rather than a
  theoretical one.
- **Per-round percentiles have only 19 reachable values**: 0, 1, 4, 9, 15, 23, 32,
  42, 52, 61, 69, 77, 83, 88, 92, 94, 96, 98, 99. Most of 0–100 is unreachable
  (nothing between 42 and 52, or 61 and 69). A 12-round × 4-player grid will show
  exact duplicate integers between unrelated cells routinely, reading as
  coincidence rather than as the metric's coarseness. Inherent and documented in
  `DealStrength.js`, but it now surfaces raw to players.
- **The old two-channel design's premise was weak**, which `6b7aaf4` made moot:
  extreme number/colour disagreement (rank 1 with percentile < 50, or rank 4 with
  percentile > 50) occurs in only 0.13% and 0.43% of rounds. Middle-rank
  disagreement was much more common (~19–22% for ranks 2 and 3), so the design was
  not information-free — but the marquee "won without the cards" case it was sold
  on fires under half a percent of the time. The pivot was the right call.
- **Rounding is clean.** `percentileFor`'s mid-rank convention returns
  half-integers by design, and the mean sums unrounded values before rounding
  once, so there is no double-rounding bias.
